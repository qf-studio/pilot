# GH-5342-2

**Created:** 2026-09-06

## Problem

## Subtask 2 of 4

**Parent Task:** GH-5342 - fix(executor): post-timeout finalization reuses the expired task ctx — committed work reported as no_op and never pushed (GH-263 ×2, pilot-console)

## Objective

`no_op` is only recorded when the commit count succeeded and returned zero with a clean worktree.

## Context

This is part of a larger task that has been decomposed for better execution.
Focus on this specific objective. Other subtasks will handle the remaining work.

## Acceptance Criteria

- A commit-count check that *fails* (e.g. `context deadline exceeded` from a
  stale ctx) is never treated as "confirmed zero commits" — it must not, by
  itself, cause `no_op` to be recorded.
- `no_op` is only recorded once the count call succeeds AND returns zero AND
  the worktree is confirmed clean (dirty real work always wins, per GH-4964).

## Resolution

Subtask 1 (GH-5342-1, commit 9fc9375f) fixed the three *finalization*
call sites (`finalizeEpicBranchPR`, the direct path's CreatePR guard, and
`finalizeDecomposedParentPR`) that discarded the commit-count error. A
fourth call site with the identical anti-pattern remained: the GH-916
no-commit-retry's **post-retry** re-check (`runner.go` ~4477, inside the
`task.CreatePR && !task.DirectCommit && task.Branch != ""` block), which
re-runs `git.CountNewCommitsAgainstOrigin` after the retry backend call and
used to discard the error, reading it as `commitCount == 0` and marking the
task `no_op` — even when the retry had legitimately landed a real commit but
only returned after the task ctx's deadline had already passed.

Fix (`internal/executor/runner.go` ~4477): capture `countErr` from the
post-retry count call and only enter the `no_op` branch when `countErr ==
nil && commitCount == 0` (a *confirmed* empty branch). A count failure now
logs a warning and falls through to the success path, deferring to the
downstream finalize block's own `finalizeCtx`-derived fresh context to
establish the real commit count before push/PR-create — mirroring the
pre-retry check just above it (`runner.go` ~4354), which already had this
exact guard from GH-4964's clean-worktree work. The `preserveDirtyOrFail`
clean-worktree check at this insertion point predates this fix (GH-4964)
and was already correct; this change closes the missing "count succeeded"
half of the `no_op` precondition.

Tests: `internal/executor/runner_gh5342_test.go` —
`TestNoCommitRetry_PostRetryCommitCountFailure_NotRecordedAsNoOp` drives a
real `Runner.Execute()` (mock backend, real git repo + fake `gh` binary):
the retry lands a real commit but returns only after a short outer task ctx
has expired, so the post-retry count call fails with `context deadline
exceeded`. Asserts the result is never `no_op` and that the branch still
gets pushed and a PR opened via the finalize block's fresh ctx.

# GH-5342-3

**Created:** 2026-09-06

## Problem

## Subtask 3 of 4

**Parent Task:** GH-5342 - fix(executor): post-timeout finalization reuses the expired task ctx — committed work reported as no_op and never pushed (GH-263 ×2, pilot-console)

## Objective

No Claude Code re-invocation happens on a context that is already done.

## Context

This is part of a larger task that has been decomposed for better execution.
Focus on this specific objective. Other subtasks will handle the remaining work.

## Acceptance Criteria

- A retry decision that would re-invoke the backend (spawn another Claude
  Code process) never fires once the task's own `ctx` is already `Done()`
  (deadline exceeded or explicitly canceled).

## Resolution

Audited every call site that re-invokes `r.backendExecute` on the bare task
`ctx` (as opposed to a deliberately fresh context):

- The GH-916 no-commit-retry (`runner.go` ~4354-4426) is already safe: its
  own gate, `git.CountNewCommitsAgainstOrigin(ctx, baseBranch)`, shares the
  same `ctx` and — confirmed empirically — `exec.CommandContext` refuses to
  even start a subprocess on an already-`Done()` ctx, so that count call
  fails first and the whole retry block (including the backend
  re-invocation) is skipped via the existing `countErr != nil` branch. No
  code change needed here; adding a redundant ctx check would just be
  validation for a case that can't occur through this path.
- The **intent-judge retry** (`runner.go` ~5149-5200, "Handle intent judge
  result") had the real gap: nothing upstream of it shares `ctx` to fail
  fast. The quality-gate retry loop that runs earlier in the same execution
  always gets its own fresh, `ctx`-independent timeout
  (`context.WithTimeout(context.Background(), timeout)`, GH-4876) and can
  burn real wall-clock while the task's own `ctx` keeps ticking
  independently. By the time the intent judge vetoes a diff, `ctx` may
  already be done — and the retry unconditionally called
  `r.backendExecute(ctx, ...)`, spawning a doomed Claude Code invocation
  that `exec.CommandContext` would refuse to start, while still marking
  `state.intentRetried = true` and consuming the one allowed retry for
  nothing.

Fix (`internal/executor/runner.go` ~5149): added an `else if ctx.Err() !=
nil` branch between the "already retried" and "run the retry" branches.
When ctx is already done, skip `backendExecute` entirely, log it, and fall
back to `result.IntentWarning = intentVerdict.Reason` — the same outcome
already used for a failed retry or an already-consumed retry — instead of
spending a doomed re-invocation.

Tests: `internal/executor/runner_gh5342_test.go` —
`TestIntentJudgeRetry_ExpiredTaskCtx_SkipsReinvocation` drives a real
`Runner.Execute()` (mock backend + real git repo + fake `gh` binary + a
mocked `IntentJudge` cmdRunner). The judge subprocess is mocked to sleep
past a short outer task ctx's deadline before returning `VERDICT: FAIL`,
reproducing a judge call that legitimately took real wall-clock time
(GH-4669) and returns only after ctx is already done. Asserts the backend
is called exactly once (the retry never fires), `IntentWarning` still
carries the judge's reason, and the initial commit still results in success
with a PR opened.

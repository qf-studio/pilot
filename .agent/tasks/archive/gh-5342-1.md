# GH-5342-1

**Created:** 2026-09-06

## Problem

## Subtask 1 of 4

**Parent Task:** GH-5342 - fix(executor): post-timeout finalization reuses the expired task ctx — committed work reported as no_op and never pushed (GH-263 ×2, pilot-console)

## Objective

A backend timeout with commits on the branch results in a pushed branch and either a PR or a `pilot-needs-human` hold; never `no_op`.

## Context

This is part of a larger task that has been decomposed for better execution.
Focus on this specific objective. Other subtasks will handle the remaining work.



## Acceptance Criteria

- A branch with real commits never gets recorded as `no_op` because a
  post-timeout `git`/`gh` call failed on the already-expired task ctx.
- A genuine `context.Canceled` (explicit stop) is still respected — only a
  blown deadline gets a fresh window.

## Resolution

Root cause: three finalization call sites shared the same anti-pattern —
`if guardCount, _ := git.CountNewCommits...(ctx, baseBranch); guardCount == 0`
— discarding the count error and reading a failure as "zero commits". Once
a long-running backend legitimately used the full task timeout, `ctx` was
already past its deadline by the time finalization ran, so every downstream
`git`/`gh` call failed instantly with "context deadline exceeded", which
this guard silently misread as an empty branch → `no_op`, discarding
already-committed, never-pushed work (GH-263 x3).

Fix (`internal/executor/runner.go`):
- Added `finalizeCtx(ctx, budget)`: if `ctx.Err() == context.DeadlineExceeded`,
  returns a fresh `context.WithTimeout(context.Background(), 5*time.Minute)`
  context for finalization (commit-count guard, push, PR/MR create). A real
  `context.Canceled` is left untouched — that's a genuine stop request, not
  an exhausted budget on otherwise-complete work.
- Applied `finalizeCtx` at the top of the three finalization paths that were
  reusing the exhausted task ctx: `finalizeEpicBranchPR` (runner.go), the
  direct path's `task.CreatePR && task.Branch != ""` block (runner.go), and
  `finalizeDecomposedParentPR` (runner_decompose.go).
- Replaced each ignored-error commit-count guard with explicit handling: a
  count failure now marks the task/epic failed with a descriptive error
  (feeding the normal retry/escalation path, e.g. toward
  `pilot-needs-human`), instead of being silently coerced into
  `guardCount == 0` → `no_op`.

Tests: `internal/executor/runner_gh5342_test.go` — unit coverage for
`finalizeCtx` (expired/canceled/live ctx) plus end-to-end regression tests
proving an epic and a decomposed-parent branch with real commits still push
and open a PR when handed an already-expired ctx, and that a genuinely
canceled ctx still fails (never `no_op`).

## Resolution

Audited every real generation-incrementing repick path in the codebase:
`nextRetryGeneration` (dispatcher.go) is the *only* generation+1 decider that
exists anywhere, and it is reached exclusively through
`beginWithGenerationRetry`, which every production dispatch channel funnels
through — `queueSingleTask` (poller path, plain tasks, and decomposed
subtasks) and `queueDecomposedTask` (decomposed parent). Subtasks 2/3 already
made that gate consult and grow the shared `repick_backoff` store row.

The "sub-issue paths" named in the issue (epic.go's `executeSubIssuesTracked`
loop) call `ExecutionLifecycle.Begin` directly at generation 0 and never
compute a generation+1 retry themselves — so they structurally cannot produce
an unthrottled repick storm: a repicked epic re-discovering an already-failed
child collides with that child's terminal generation-0 claim and loses
(`ErrClaimLost`) without invoking the backend a second time. Pinned this as a
regression guard with `TestExecuteSubIssues_RepickDoesNotBypassBackoff`
(internal/executor/epic_repick_backoff_test.go) plus a doc comment at the
Begin() call site (epic.go) so a future generation+1 retry added there is
required to route through the same shared store.

Also pinned cmd/pilot's and internal/executor's independently-duplicated
`repickBackoffKey` format (`projectPath + "|" + taskID`) to the identical
literal in both packages (`TestRepickBackoffKey_FormatMatchesDispatcherPackage`
in cmd/pilot, `TestRepickBackoffKey_FormatMatchesCmdPilotPackage` in
internal/executor) — the "one shared per-task backoff" promise depends on
both sides computing the exact same key string, and there was previously no
test catching a silent divergence.

Subtask 4/5 of GH-4394; a hard consecutive-failure cap (mark task `stalled` +
alert) is tracked separately as subtask 5.

## Confirmed findings (47) — from workflow output

### critical

- **Retry executions run in task.ProjectPath, not the worktree — retries can't recover and mutate the user's real repo**
  - dim: `executor-core` · file: `internal/executor/runner.go:2197, 2561` · cat: bug · conf: high
  - The primary execution runs the backend with ProjectPath: executionPath (the isolated git worktree created at runner.go:1253), and all post-execution verification (git.CountNewCommits, ghost-SHA guard, push) runs via git := NewGitOperations(executionPath) at runner.go:1612 — i.e. against the worktree. But BOTH retry paths pass ProjectPath: task.ProjectPath instead: the smart retry (line 2195-2197) and the no-commit retry (line 2559-2561). task.ProjectPath is never reassigned to the worktree (confirmed via grep — no `task.ProjectPath = ` anywhere). Consequences when worktrees are enabled (the default for any task with Branch != "" && !DirectCommit, which is exactly the condition that also gates the worktree creation AND the no-commit retry): (1) Claude on retry runs in the original repository working directory, so its commits land on whatever branch the real repo HEAD is on (or pollute the user's uncommitted working tree), defeating the GH-936 worktree isolation guarantee. (2) The subsequent commitCount = git.CountNewCommits(ctx, baseBranch) check (line 2594) still inspects the worktree, which the retry never touched, so it always reports 0 commits — the retry is structurally incapable of clearing the no_changes failure. So the no-commit retry and the smart timeout/rate-limit/API/OOM retries are simultaneously ineffective (never recover) and dangerous (write to the wrong tree).
  - fix: Change both retry ExecuteOptions to ProjectPath: executionPath so retries run in the same worktree the primary execution and all commit checks use. Add a regression test asserting that when UseWorktree is enabled, the retry backend invocation receives the worktree path, not task.ProjectPath.

- **Shared *PRState pointers mutated across goroutines without holding the controller mutex**
  - dim: `concurrency` · file: `internal/autopilot/controller.go:455-527, 444-448, 2487-2537, 2233-2264` · cat: bug · conf: high
  - The autopilot Controller stores *PRState in activePRs and hands the LIVE pointers out under c.mu, then mutates the struct fields with NO lock held. GetActivePRs() (line 1910) returns the live pointers; processAllPRs (2498) reads pr.Stage/pr.CIStatus outside any lock and ProcessPR (455-457) does `c.mu.RLock(); prState = c.activePRs[n]; c.mu.RUnlock()` then writes prState.PRTitle/TargetBranch/Stage/Error (472-527) with the lock released. The stage-machine handlers also mutate prState.Stage. Concurrently, OnReviewRequested (444-446, a webhook-driven goroutine) writes prState.Stage under c.mu, and the reconciler goroutine (startReconciler launched at 2433) registers/touches PRs. So three independent goroutines — the main poll loop, the 60s reconciler, and webhook callbacks (OnReviewRequested/OnPRCreated) — read and write the SAME *PRState fields, but the mutex only guards the map lookup, never the struct it points to. This is a genuine multi-goroutine data race far broader than the known *prFailureState issue at ~1984: torn reads of Stage can drive the wrong state-machine branch (silent wrong-action: e.g. merging a PR whose stage was concurrently reset to ReviewRequested) and is detectable under `go test -race`.
  - fix: Either (a) guard ALL *PRState field access with c.mu (add helper getters/setters and never mutate fields outside the lock), or (b) make GetActivePRs/ProcessPR operate on value copies and write results back via a locked store method. Lowest-risk: add a per-PRState sync.Mutex and lock it around the read-modify-write region in ProcessPR, OnReviewRequested, processAllPRs, and persistPRState. Add a `go test -race` test that drives processAllPRs and OnReviewRequested on the same PR concurrently.

- **Data race on shared *PRState between webhook handlers and the autopilot processing loop**
  - dim: `autopilot` · file: `internal/autopilot/controller.go:444-446 (OnReviewRequested), 1159-1185 (SetApprovalDecision), 483-534 (ProcessPR handlers)` · cat: reliability · conf: high
  - PRState objects are mutated lock-free inside the stage handlers invoked from ProcessPR/processAllPRs (the entire `switch prState.Stage` block and ~30 `prState.Stage = ...` / `prState.HeadSHA = ...` / `prState.ConsecutiveAPIFailures++` writes at lines 567-1874 hold NO lock — ProcessPR only takes c.mu.RLock to read the map pointer, then releases it). - **GitHub 403 secondary/primary rate limits are not retried and the Retry-After HTTP header is never read**
  - dim: `github-adapter` · file: `internal/adapters/github/retry.go:55-62, 95-136, 141-173` · cat: reliability · conf: high
  - GitHub signals secondary rate limits (and primary REST limits) with HTTP 403 plus a Retry-After or X-RateLimit-Reset HTTP header — not 429, and not body text. isRetryableError (retry.go:95) explicitly excludes 403 ('403 Forbidden (non-rate-limit)', line 92), so secondary-limit 403s fail immediately with no retry. Separately, doRequest builds the error as `API error (status %d): %s` from resp.StatusCode + body bytes only (client.go:165-166); resp.Header is discarded. extractRetryAfter (retry.go:141) then regex-scans that error STRING for 'Retry-After: N', but GitHub puts Retry-After in the HTTP header, not the JSON body, so the regex effectively never matches a real GitHub response. The doc comment 'It respects context cancellation and GitHub's Retry-After header' (retry.go:28) is therefore inaccurate. Net effect: under bursty load (poller AddLabels/RemoveLabel/AddComment churn, board writes) Pilot can hit secondary limits and surface immediate hard failures, which in the poller flow can mislabel issues pilot-failed.
  - fix: In doRequest, when status is 403 or 429, read resp.Header.Get('Retry-After') and resp.Header.Get('X-RateLimit-Remaining')/('X-RateLimit-Reset') and encode them into a typed error (e.g. a RateLimitError carrying RetryAfter time.Duration). Make isRetryableError treat 403-with-secondary-rate-limit (body contains 'secondary rate limit' or 'rate limit exceeded', or X-RateLimit-Remaining:0) as retryable, and have WithRetry honor the parsed header duration instead of regexing the message string.

- **Dispatcher project workers are never removed from the workers map — goroutine accumulation and broken stale-recovery**
  - dim: `concurrency` · file: `internal/executor/dispatcher.go:434-460, 302-307` · cat: reliability · conf: high
  - ensureWorker adds a *ProjectWorker to d.workers under d.mu and launches a goroutine running worker.Run, but nothing ever deletes from d.workers — there is no `delete(d.workers, projectPath)` anywhere (confirmed by grep). ProjectWorker.Run never returns until ctx is cancelled or Stop() is called, so each distinct project path keeps a goroutine blocked on its signal/stop channel for the daemon's whole lifetime. Two concrete consequences: (1) goroutine + map growth proportional to the number of distinct project paths ever seen (unbounded for a multi-repo daemon), and (2) hasLiveWorker(projectPath) (302) — used by recoverStaleTasks to decide whether an orphaned task may be reaped — returns true forever once a project has been seen, so genuinely orphaned running/queued tasks for that project are never reaped. The stale-recovery safety net is silently disabled per-project after first use.
  - fix: When a worker's queue drains and it exits its idle window, remove it from d.workers under d.mu (or have Run signal the dispatcher to delete on return). Alternatively, decouple hasLiveWorker from the map: track an `atomic.Bool processing` per worker and have hasLiveWorker mean 'worker actively processing this project' rather than 'worker object exists', so reaping resumes once a worker goes idle.

- **API backend retry backoff uses time.Sleep, ignoring context cancellation**
  - dim: `error-resource` · file: `internal/executor/backend_anthropic.go:353, 365, 386 (and openai 263, 273)` · cat: reliability · conf: ?
  - AnthropicBackend.callAPI and OpenAIBackend.callAPI retry on HTTP/5xx/429/overloaded errors by calling time.Sleep(backoffs[...]) directly inside the loop. backoffs grows to 180s and there are apiMaxRetries attempts, so a single API call can sit in unconditional sleeps for many minutes. The ctx passed in is the long-lived task execution context (callAPI(ctx) is invoked from Execute at backend_anthropic.go:608). During daemon shutdown, task timeout, or explicit cancellation, ctx.Done() fires but the goroutine keeps sleeping — the cancellation is silently deferred until the sleep elapses. The GitHub client retry (internal/adapters/github/retry.go:64-70) does this correctly with `select { case <-ctx.Done(): return ctx.Err(); case <-time.After(delay): }`, so the project already has the right pattern; the API backends just don't use it.
  - fix: Replace each `time.Sleep(wait)` in the retry loops with a context-aware wait, e.g.: ```go select { case <-ctx.Done():     return nil, ctx.Err() case <-time.After(wait): } ``` This makes cancellation/shutdown responsive while preserving backoff timing.

- **SMTP alert sender discards the context, so the dispatcher's delivery timeout is never enforced**
  - dim: `error-resource` · file: `internal/alerts/smtp.go:31, 49` · cat: reliability · conf: ?
  - Dispatcher.sendToChannel wraps each channel delivery in a 30s timeout context (internal/alerts/dispatcher.go:177-181) and calls ch.Send(ctx, alert). EmailChannel forwards to EmailSender.Send(ctx, ...), but SMTPSender.Send signs the context as `_ context.Context` and calls net/smtp.SendMail, which opens a raw TCP connection with no deadline. If the SMTP server accepts the connection but stalls (hung/blackholed mailserver, dropped packets), SendMail blocks on OS-level TCP timeouts (often minutes), not the intended 30s. Because alert dispatch goroutines are spawned per-channel and the result is collected, a stuck SMTP send ties up a goroutine and delays/forfeits the timeout guarantee the dispatcher believes it has — degrading the very alerting path meant to surface incidents.
  - fix: Honor the context: dial with a deadline and abort if ctx expires, e.g. use net.Dialer{}.DialContext(ctx, "tcp", addr) to obtain a conn, wrap with smtp.NewClient, set conn deadlines, and run StartTLS/Auth/Data; or run SendMail in a goroutine and select on ctx.Done() to fail fast (closing the conn). At minimum set a net.Conn deadline derived from the context.

- **Single-threaded alert event loop + synchronous 30s dispatch lets one hung channel drop ALL alerts (incl. critical PagerDuty escalations)**
  - dim: `alerts-observability` · file: `internal/alerts/engine.go:131,168-169,107,150-157,543` · cat: reliability · conf: high
  - processEvents runs in ONE goroutine (engine.go:131). For each event it calls handleEvent synchronously, which for failures/escalations calls fireAlert -> dispatcher.Dispatch, and Dispatch blocks until every channel returns (dispatcher.go:124-128 wg.Wait). Each channel send has a 30s timeout (dispatcher.go:178). So a single slow/hung channel (e.g. a webhook or SMTP endpoint that stalls) blocks the entire event loop for up to 30s per fired alert. eventCh is a buffered channel of only 100 (engine.go:107); ProcessEvent does a non-blocking send and silently drops on overflow (engine.go:150-157). Under a failure storm or a hung channel, the queue fills and subsequent events — including EventTypeEscalation / EventTypeOOMKilled / consecutive-failure criticals — are dropped with only a Warn log. The MetricsAlerter pushes an autopilot_metrics event every 30s through the same queue, so a stall guarantees these pile up. Net effect: the exact moment alerting matters most (cascading failures), alerts are silently lost.
  - fix: Decouple firing from the event loop: have fireAlert dispatch on its own bounded worker pool (or `go e.dispatcher.Dispatch(...)` with a semaphore) so handleEvent never blocks on channel I/O. Additionally, when eventCh is full, prefer dropping low-severity events over critical/escalation (e.g. a small priority queue, or a dedicated unbuffered escalation path), and emit a counter on every drop so loss is observable.

# GH-5342-4

**Created:** 2026-09-06

## Problem

## Subtask 4 of 4

**Parent Task:** GH-5342 - fix(executor): post-timeout finalization reuses the expired task ctx — committed work reported as no_op and never pushed (GH-263 ×2, pilot-console)

## Objective

Daemon log for the finalization phase shows no `context deadline exceeded` from git/gate calls after a backend timeout.

## Context

This is part of a larger task that has been decomposed for better execution.
Focus on this specific objective. Other subtasks will handle the remaining work.

**Note:** This is the final subtask. Ensure all previous subtasks are complete before finishing.

## Acceptance Criteria

- After a backend run legitimately uses the full task timeout, the daemon
  log contains no Warn-level "context deadline exceeded" text from the
  post-backend git/gh verification calls (no-commit-retry pre/post
  commit-count checks, ghost-SHA check, dirty-worktree auto-preserve).
- Where the underlying git call is itself the intended fast-fail gate for a
  retry/backstop decision (documented in GH-5342-3's resolution), the
  outcome is unchanged — only the log level for the *expected*,
  already-Done()-ctx case is affected.
- Where the underlying git call is actually trying to save
  already-completed work (the GH-4517 dirty-worktree auto-preserve
  commit+push), it gets a fresh, bounded window instead of failing on the
  stale ctx, so the work is actually preserved rather than merely logged
  more quietly as lost.

## Resolution

Three of the four remaining post-backend git call sites that still shared
the task's own (possibly already-expired) ctx were, per GH-5342-3's audit,
*intentionally* left as-is: their fast failure on a dead ctx is what gates
the no-commit-retry and ghost-SHA backstops without needing an explicit
`ctx.Err()` check. That's correct control flow, but every one of those
fast failures logged at `Warn` with the raw `"context deadline exceeded"`
error text — daemon-log noise indistinguishable from a real git/gh problem,
for what is actually the designed, expected outcome of a backend run using
its full timeout.

Fix (`internal/executor/runner.go`, `internal/executor/git_freshness.go`):

- Added `logGitCtxErr(ctx, log, msg, attrs...)` (runner.go, next to
  `finalizeCtx`): logs at `Warn` normally, but downgrades to `Debug` when
  `ctx.Err() != nil` — the call failed only because the task ctx was
  already `Done()`, not because of an unexpected git/gh problem. At the
  daemon's default (Info) log level, these entries are no longer emitted.
- Applied `logGitCtxErr` to the three classification-only call sites that
  deliberately keep sharing the task ctx as their fast-fail gate:
  - the no-commit-retry pre-retry commit-count check (runner.go ~4354)
  - the no-commit-retry post-retry commit-count re-check (runner.go ~4477)
  - the ghost-SHA `commitSHAIsNew` check (git_freshness.go, `applyGhostSHAGuard`)
- For the fourth site — `preserveDirtyWorktreeAsWIP`'s commit+push
  (git_freshness.go), the GH-4517 backstop that auto-commits and pushes
  genuinely uncommitted work before the worktree gets deleted — a log-level
  downgrade alone would have hidden a real problem: this call is itself
  trying to *save* already-completed work, the exact case `finalizeCtx`
  exists for (GH-5342-1). Wrapped its ctx with `finalizeCtx(ctx,
  finalizeGitTimeout)` instead, so an exhausted task ctx no longer causes
  real dirty work to be silently reported as "nothing to preserve" and
  discarded by the deferred worktree cleanup.

Tests: `internal/executor/runner_gh5342_test.go` —
`TestNoCommitRetry_PostRetryExpiredCtx_NoDeadlineExceededLogNoise` reruns
subtask 2's real-`Runner.Execute()` scenario (a GH-916 retry that lands a
real commit but returns only after the outer task ctx's deadline has
blown) with the runner's logger pointed at a buffer, and asserts the
captured daemon-log text never contains `"context deadline exceeded"`.

**Created:** 2026-08-24

## Problem

GitHub Issue GH-5063: Root repo core.bare flips to true when SIGTERM kills a pre-push gate mid-run (3rd occurrence; writer still unidentified)

## Summary

`.git/config`'s `core.bare` has flipped from `false` to `true` three times (2026-07-28, 2026-08-18, 2026-08-21), always correlated with a `git push` being SIGTERM'd (2-min timeout) while `scripts/pre-push-gate.sh`'s `go test -short -race ./...` step (measured 188-238s, see `.agent/sops/quality/pre-push-gate.md`) was still running. Because worktrees share `.git/config`, the flip breaks `git status`/build/lint/test for EVERY concurrent session (root + all linked worktrees), not just the pusher — repo-wide, not cosmetic.

## What's confirmed

- No script/hook in this repo (`scripts/*.sh`, `.git/hooks/pre-push`) or Go code (`internal/`, `cmd/`) writes `core.bare`, `--bare`, `GIT_DIR`, or `--work-tree` — verified by grep across three separate investigations.
- No trap/cleanup exists anywhere in the pre-push scripts (grep for `trap ` returns nothing), so there's no restore-on-EXIT-but-not-TERM asymmetry — nothing ever unwinds `core.bare` because nothing sets it locally.
- The measured full-gate runtime (224-287s) exceeds a 120s SIGTERM window by construction, so the hang is expected/reproducible, not a network stall.
- The actual writer of `bare=true` remains **unidentified** after 3 incidents.

## Ask

1. Raise the timeout on any automation that `git push`es against this repo to ≥300s, or route non-interactive pushes through `--no-verify` + CI-side gating (CI runs the same gates).
2. Add a defensive pre-flight (`git rev-parse --is-bare-repository`) to session-start tooling (pilot-board / nav-start hook) that auto-corrects and logs a `core.bare=true` drift instead of requiring manual triage each occurrence.
3. Instrument the next reproduction with `GIT_TRACE=1`/`GIT_TRACE_SETUP=1` or a `.git/config` mtime watch to actually catch the writer — static code review has been exhausted across 3 attempts.

## Implementation (tripwire so occurrence №5 names the writer)

Investigation is stuck at "writer unidentified" after 4 occurrences — flip the approach: instrument, wait, catch.

- Add a small shell watcher (name it git-config-watch, place it in the scripts directory alongside the existing CI check scripts) that polls the repo root's git config value of core.bare every 2–5 s. On a flip to true it must capture, before healing: timestamp, the config file's mtime, lsof holders of the config file, and a process-table snapshot with parent chains — appended to a log file under the system temp directory. Then auto-heal (set core.bare back to false) with a loud log line.
- Document (README section in the script header is fine) how to run it ad hoc in tmux on the laptop and on the founder box — both are push contexts where the pre-push gate runs.
- Encode the known negatives in the script header: 2026-08-24 — a SIGTERM killing the pre-push gate mid-run (during go test -short) did NOT reproduce the flip, so the original hypothesis is weakened; the watcher must not assume the gate is the writer.

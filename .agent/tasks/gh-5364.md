## Problem

GitHub Issue GH-5364: test(executor): make the #5353 re-arm race tests regression-sensitive — same-second stall stamps and a poller-pickup step that only exists in comments

Note: the two test files below are on PR #5363's branch and land on main when it merges; start this issue from main after that merge.

PR #5363 (issue #5353) fixed `escalateStalledTask` correctly, but its tests pass with the fix reverted:

1. The executor race test added by PR #5363 (file gh5353_stalled_rearm_race_test, in the executor package; lines ~69-76): the two `stallTaskAfterRepickHardCap` calls execute within one `CURRENT_TIMESTAMP` second, so `completed_at` compares equal to T0 even when the second escalation re-stamps it. Verified 5/5 green against main's pre-fix dispatcher.
2. The interleave test added by PR #5363 (file gh5353_rearm_interleave_test, in the cmd/pilot package; lines ~30-81): the "simulated poller pickup" step is comments only; the test never calls `escalateStalledTask`, so it duplicates `TestTryRearmStalled_PilotRetryReadyLabelAfterStall_Rearms` and cannot detect the race.

## Fix

1. Executor test: make the second escalation observably later than the first without wall-clock sleeps — seed the stalled row's `completed_at` well in the past (e.g. via `SaveExecution` with an explicit timestamp, as `seedStalledRow` in `cmd/pilot` does) and assert it is unchanged after the repeat escalation; assert that with the early-return removed the value would move (mutation-style assertion on the pre-fix code path is not required, but the fixture must fail on a re-stamp).
2. Interleave test: actually drive the race — stall at T0 (seeded past), record the re-arm label event at T1 > T0, then call the dispatcher's stall escalation for the same task at T2 > T1 through the real code path, then run the sweep and assert it re-arms. Remove the comment-only step.
3. Keep the negative tests as boundary coverage.

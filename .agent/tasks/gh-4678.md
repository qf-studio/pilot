# GH-4678

**Created:** 2026-08-03

## Problem

GitHub Issue GH-4678: feat(cli,executor): no way to cancel a task — 'stalled' is read as retry-me and spins generations; add a real terminal cancel

## Context

Discovered 2026-08-03 during the TASK-437 cleanup: **there is no way for an operator to cancel a task.** Closing the GitHub issue does not stop it, and the documented ledger workaround actively makes it worse.

Observed sequence (box, project startups/pilot):

1. Operator closes issue #4655 as `not planned` at ~11:55Z. A queued execution row for it survives — nothing revalidates issue state at pickup (that gap is #4656, in flight).
2. Operator marks the queued row `status='stalled'` (the workaround documented in `.agent/sops`/pilot-aws skill for orphaned rows, exact-id UPDATE).
3. Dispatcher immediately re-claims: `"dispatch re-pick: prior claim was stall-killed — claiming next generation without counting toward repick hard cap" task_id=GH-4655 generation=3 consecutive_stall_drops=1`.
4. Loop: every stall produces a fresh generation, explicitly exempt from the repick hard cap. Only closing the issue AND repeated stalls eventually settled it (gen-3), and the poller ALSO re-dispatched the closed issue once at 12:03:31Z (`"Execution failed without PR, unmarking for retry" number=4655` — on an issue closed 8 minutes earlier).

So `stalled` means "dead owner, retry me" — a *recovery* signal, not a *cancel* signal. Using it as cancel is a documented footgun that spins generations.

## Acceptance

1. **A real cancel verb**: `pilot task cancel <task-id> [--project <path>] [--reason "..."]` (CLI; the daemon already owns the ledger — route through `ExecutionLifecycle` so there is one chokepoint per TASK-404). Semantics:
   - Terminal status that the dispatcher NEVER re-picks (new vocabulary value, e.g. `canceled`, distinct from `stalled`/`failed`/`no_op`) with the operator reason recorded.
   - Cancels the queued row; if the task is currently RUNNING, either refuse with a clear message naming the PID/execution id (v1, acceptable) or stop it cleanly — state which was implemented and why.
   - Suppresses poller re-dispatch for that task_id until its issue is re-opened/re-labeled (i.e. the retry-unmark path must respect a canceled terminal row).
   - Journals an event; prints what it did.
2. **Dispatcher honors it**: `nextRetryGeneration`/re-pick logic treats `canceled` as terminal — no generation+1, no cap exemption. Table-test the claim-admission matrix for the new status.
3. **Poller honors it**: the "Execution failed without PR, unmarking for retry" path must not re-dispatch a task whose latest row is `canceled` (and, separately, should not re-dispatch a CLOSED issue at all — coordinate with #4656 rather than duplicating it).
4. **Docs**: update the ops SOP + `pilot-aws` skill troubleshooting table to point at `pilot task cancel` and to explicitly warn that marking rows `stalled` is a RECOVERY signal, not a cancel.
5. Regression tests: canceled row is never re-picked across N poll cycles; stalled row still re-picks (unchanged); cancel of a non-existent/terminal task is a clean no-op with a useful message.
6. `make build`, `make test`, `make lint` green.

## Implementation

Chokepoint is `ExecutionLifecycle` (`internal/executor/lifecycle.go`, TASK-404) — add the transition there, not in ad-hoc SQL. CLI subcommand under the existing `task` command group. Status vocabulary lives alongside the other `ExecStatus*` constants; mind the SQL CHECK/consumers that enumerate statuses (dashboard, metrics filters).

Out of scope: killing a running child process safely (call it out explicitly if deferred), UI/TUI affordance.

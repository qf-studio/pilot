# GH-4808

**Created:** 2026-08-07

## Problem

GitHub Issue GH-4808: fix(approval): Slack asks land in an unwatched bot DM — channel-first destination policy + resolved-destination logging

## Problem

Slack approval asks are effectively invisible to the operator. `SlackHandler.resolveChannel` (`internal/approval/slack.go`) prefers `Approvers[0]` over the handler's configured channel — so with an approver configured, every approval request goes to a **DM with the Pilot Bot**, and `adapters.slack.approval.channel: '#pointer'` is dead config. Incident 2026-08-08: PR#4806 (size-floor escalation) sat in `awaiting_approval` for ~50 minutes while the operator searched `#pointer` and Telegram; the ask was in an unwatched bot DM. Diagnosis required Slack-side message search because the submit log line (`async approval request submitted ... channel=slack`) records only the handler name, not the resolved destination.

Note #4782 (GH-4772) deliberately made `resolveChannel` the single destination seam so first-send and rehydrate agree — this issue changes the *policy* inside that seam, not the seam itself.

## Acceptance

1. **Channel-first destination policy** in `resolveChannel`: when the handler has a configured channel, post there; fall back to `Approvers[0]` (DM) only when no channel is configured. Since it's the single seam, send/rehydrate/sweep inherit the change automatically — do not add a second resolution site.
2. **@-mention the approver**: when `Approvers[0]` is set and the destination is a channel, the message text mentions the approver (`<@U…>`) so it notifies rather than scrolls by.
3. **Existing pending rows unaffected**: message updates (`UpdateInteractiveMessage`) already use the per-row stored `Channel` from the original post — verify with a test that a pending row created under the old DM policy still updates in the DM after the policy change (no re-homing of live messages).
4. **Resolved destination in the submit log**: the `async approval request submitted` log line (approval manager or handler) gains the resolved destination (channel name/ID or DM target), so "where did the ask go" is answerable from `daemon.log` alone.
5. Tests: destination table (channel+approver → channel with mention · approver only → DM · channel only → channel · neither → handler default) · rehydrate resolves identically to first-send · log line carries destination.
6. `make build` / `make test` / `make lint` green.

## Scope fence

Slack handler + submit logging only. No Telegram changes (its destination model is chat-id based and working). No per-project destination overrides (explicitly deferred by TASK-456 — this is a global policy fix). No approval-manager routing changes (TASK-454 owns channel *selection*; this is destination *within* the Slack channel handler).

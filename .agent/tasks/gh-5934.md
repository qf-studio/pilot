## Resolution (per defect)

1. **FastTimeout cannot catch a restored 60 s** — fixed. The task ctx is now an `expirableCtx` the mock judge expires itself (no timer), so nothing waits on a budget. The injected judge timeout is pinned by `TestIntentJudge_InjectedTimeoutBoundsJudgeCtx_GH5924` with a generous 30 s task ctx, so only the injected timeout can release the mock. Mutation check: removing `SetJudgeTimeout(judgeTestTimeout)` → FAIL after 60.33 s ("judge ctx deadline is 1m0.09s after Execute began, want ~200ms"). With it: PASS 0.54 s.
2. **Task ctx cut 2 s → 1 s** — fixed by removing the wall-clock budget entirely (`expirableCtx`), so the setup-vs-deadline race no longer exists.
3. **No change to intent_judge.go** — false positive. `IntentJudge.judgeTimeout` (60 s default, `intent_judge.go:67`) and `SetJudgeTimeout` (`intent_judge.go:78`) already exist on `origin/main` (added in 78cf8166 / #4685, used by `runner.go:1572`, covered by `intent_judge_test.go:247`). No production change is needed; the injection point already exists and the new test exercises the real `IntentJudge`.
4. **Doc comment misplaced** — fixed; `waitForExecStatus` and `pollUntil` each have their own comment.
5. **Step 3 partial** — fixed: `shortSleep` (d/3, floor 10 ms under `-short`) used for the settle/negative-check sleeps incl. the 50 ms one in `TestDispatcher_MultipleProjects`; the 150 ms adoption sleep became `pollUntil`. The 1100 ms `created_at` sleep is intentionally untouched (correctness input). Remaining 10–20 ms sleeps are poll intervals.
6. **Step 4 partial** — fixed: `t.Parallel()` added to complexity/effort classifier and prompt-builder tests (plus parser/signal). Removed it again from the two haiku tests that race 100–200 ms server sleeps against client timeouts (reviewer note).
7. **PR evidence** — below.
- Reviewer notes: skip message restored on `TestConfigureProcessGroupWaitDelayBoundsCmdWait`; `pollUntil` now `t.Fatalf`.

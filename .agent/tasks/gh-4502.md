# GH-4502

**Created:** 2026-07-22

## Problem

GitHub Issue GH-4502: fix(dispatcher): stall-killed generations burn the repick hard cap — 4 stalls wedge a healthy task

## Problem

Stall-killed generations count toward `dispatcherRepickHardCap=5` exactly like real code failures. Incident: pilot-console GH-24 (2026-07-22) — 4 identical stall-watchdog kills (each a healthy session in a long silent model turn) consumed 4 of the 5 generations; the task wedged at the hard cap and required manual re-arm (delete `repick_backoff` row). A healthy-but-slow task self-destructed in ~20 minutes.

## Root Cause

`terminalExecutionStatuses` includes `"stalled"` (`internal/executor/dispatcher.go:46`), but `HasTerminalCompletion` (`internal/memory/store.go:1125-1144`) only accepts `completed`/error-free `no_op` — so a stalled row is "terminal but not done" and `beginWithGenerationRetry` increments `consecutiveDrops` (`dispatcher.go:1142`) on every re-pick, tripping the cap at `dispatcher.go:1125-1128`. Carve-outs already exist for two other non-culpable drop classes — operator cancels (`priorClaimWasOperatorCancelled`, `dispatcher.go:946-965`, consulted at `:1065`) and restart churn (boot reconciliation clears repick state, `dispatcher.go:318-335`, #4455) — but none for `"stalled"`. The #4484 outcome taxonomy classifies stall as its own class (`internal/executor/runner.go:189-221`, `:2902-2940`) but that classification is telemetry-only and never consulted by hard-cap accounting.

## Fix

Mirror the existing carve-out pattern in `beginWithGenerationRetry` (`internal/executor/dispatcher.go`): when the prior claimed execution's status is `"stalled"`, do NOT increment the shared `consecutiveDrops` counter.

IMPORTANT constraint — this must NOT be a pure unlimited bypass. Until the silent-turn stall root cause ships (sibling issue), a complex-lane task can stall deterministically on every generation; a pure bypass would retry forever and burn tokens. Instead:

1. Track stall-kill drops in a separate counter (persisted alongside the existing repick/backoff state) with its own, higher cap (default 8, constant next to `dispatcherRepickHardCap`).
2. When the stall cap is hit, take the same escalate-and-hold path as the hard cap (`stallTaskAfterRepickHardCap` or equivalent) but with a truthful, distinct reason string identifying repeated stall-kills — not the generic hard-cap message — so the operator immediately knows it is the stall class, not failing code.
3. Existing behavior for `failed`/`infra`/operator-cancel/restart-churn drops is unchanged. Whether `"infra"` deserves the same carve-out is explicitly OUT OF SCOPE for this issue — note it in the PR body if touched code makes it trivial, but do not implement.

## Acceptance Criteria

- Table-driven test: 4 consecutive `stalled` drops + 1 `failed` drop → task is NOT wedged (shared counter reflects only the non-stall drop).
- Table-driven test: stall-drop count reaching the stall cap → task escalates/holds with the distinct stall-class reason string.
- Table-driven test: operator-cancel and restart-churn carve-out behavior unchanged (regression guard around `dispatcher.go:1065` and `:318-335` semantics).
- Mixed sequence test: stalled drops interleaved with failed drops — each counter advances independently; hard cap still trips at 5 genuine failures.
- `go test ./internal/executor/...` green; `make lint` clean.

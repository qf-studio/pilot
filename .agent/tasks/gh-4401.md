# GH-4401

**Created:** 2026-07-18

## Problem

GitHub Issue GH-4401: P0: subprocess_limits RLIMIT_AS cap breaks ALL Claude Code executions on Linux — fetch failed in 25ms, 12h of zero completions post-cutover (GH-3028 latent)

## Problem

After the S6-lite cutover, **100% of executor task executions failed** with `unknown: exit status 1` after ~3 minutes, 0 tokens. Inside the subprocess: every Anthropic API request died in ~25ms with undici `fetch failed` (`API error (attempt N/11): undefined Connection error.`) despite TCP connect success and `TLS secureConnect authorized: true`. Queue churned for ~12h total (shadow-ledger era + post-#4393-recovery era) with zero completions.

## Root cause

`subprocess_limits` (GH-3028) implements the "RSS cap" as **`RLIMIT_AS` (virtual address space) via prlimit64** — `internal/executor/backend_claudecode.go:462` / `applyResourceLimits`. With `max_rss_mb: 4096`, executor children get a 4GB **address-space** cap. Node 22/V8 reserves far more *virtual* memory than RSS (pointer cage, code ranges, io_uring/undici buffers); mmap failures inside fetch surface as instant generic `fetch failed` — the CLI itself keeps running.

**The cap is a documented no-op on darwin** — it never fired on the founder's laptop. First Linux daemon (the EC2 box) activated the latent bug.

## Evidence

- Live executor children: `Max address space 4294967296` (/proc/<pid>/limits); daemon-side judge/classifier children (different spawn path, no `applyResourceLimits`): `unlimited` — judges worked all along, tasks never did
- Full elimination series on the box: same binary/env/flags/cwd/prompt/cgroup/session succeed manually every time (rlimits were the only inherited-through-sudo difference; a `sudo -iu` re-exec wrapper still failed, which is what pinned inheritance)
- `NODE_DEBUG=tls` + `ANTHROPIC_LOG=debug` capture: handshake `authorized: true` → `connection failed - error; no more retries left { url: 'https://api.anthropic.com/v1/messages?beta=true', durationMs: 25, message: 'fetch failed' }`
- Fix confirmed: with the cap disabled, first execution completed immediately (GH-96 → 13,623 tokens, pilot-canary-sandbox PR #98, 2026-07-17 09:40:42Z)

## Workaround applied on the box (2026-07-17 09:33Z, operator-authorized)

`subprocess_limits.enabled: false` in `~/.pilot/config.yaml` (backup: `config.yaml.bak-4396`) + daemon restart. **OOM protection is now OFF** — the original GH-3028 motivation (runaway Claude subprocesses) is unmitigated until the proper fix.

## Fix

1. Replace `RLIMIT_AS` with a mechanism that caps RSS, not VA: cgroup v2 transient scope per child (`memory.high`/`memory.max`), which the daemon can create on Linux; keep darwin no-op
2. Alternatively/additionally pass `NODE_OPTIONS=--max-old-space-size=<mb>` to bound the V8 heap cooperatively
3. Preflight guard: on startup, if `subprocess_limits.enabled` with RLIMIT_AS implementation, refuse or warn loudly on Linux
4. Keep RSS telemetry (sampler) decoupled from the cap so disabling the cap doesn't lose observability
5. Table-driven test: spawn a Node child under the configured limit and assert an HTTPS fetch succeeds — would have caught this before cutover

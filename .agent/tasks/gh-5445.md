# GH-5445

**Created:** 2026-09-13

## Problem

GitHub Issue GH-5445: fix(dispatcher): treat an auto-preserved dirty worktree as a deterministic failure and escalate with the preserved sha, instead of re-picking from origin/main

## Problem

When a run ends with `worktree had uncommitted work at no-op classification — auto-preserved as <sha> on branch <branch>; needs manual review, not a genuine no-op` (`internal/executor/git_freshness.go`), the dispatcher treats it as an ordinary retryable failure. Observed on 2026-09-13 for console GH-308 (box daemon.log 16:21:35Z to 16:22:20Z): the auto-preserve landed `0e704c0` on `pilot/GH-308`, and 36 s later `dispatch re-pick: prior claim was terminal but task is not done — claiming next generation for retry` started generation 5 from scratch:

1. `CreateWorktreeWithBranch` in `internal/executor/worktree.go` runs `git worktree add -B <branch> <path> origin/main`, which resets the local branch and discards the preserved commit from the new run's view.
2. The executor's push in `internal/executor/git.go` is a plain `git push -u origin <branch>`, so even a successful re-run cannot land: the remote branch already holds the preserved commit and the push is non-fast-forward.
3. The error text says "needs manual review", but nothing escalates; the issue gets no comment naming the preserved sha, and the only signal is the daemon log. The preserved work for GH-308 was complete (build, vet, tests, lint all green) and would have been overwritten or stranded without an operator noticing.

## Fix

1. Classify the auto-preserve outcome as a deterministic failure: `IsPermanentFailure` (or the predicate `priorClaimWasDeterministicFailure` consults) recognises the `auto-preserved as` error shape, so the next poll tick routes the task to `escalateDeterministicFailure` instead of `nextRetryGeneration`. No fresh generation, no repick backoff burn.
2. The escalation comment on the originating issue must name the preserved sha and branch and say what to do next: fetch the branch, review the commit, and either open the PR from it or file a continuation issue that cherry-picks it. Reuse the existing operator-attention comment path; do not add a new comment type.
3. `runner.go`'s second auto-preserve site (the dirty-worktree path around the `auto-preserved dirty worktree` log line) gets the same classification, so both producers are covered.
4. No change to the auto-preserve itself, to worktree creation, or to the push command.

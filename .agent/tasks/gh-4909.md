## Problem

PR#4908 (GH-4872 base-branch guard) merged with two review defects that must close before the guard is trustworthy — full analysis in the PR#4908 review comment.

**1 (HIGH). Stale `TargetBranch` cache defeats the guard in both directions.** `internal/autopilot/controller.go:2065` populates `prState.TargetBranch` from `ghPR.Base.Ref` only when empty and never refreshes it; the base-mismatch guard re-reads only when empty.
- Parked PR whose base a human retargets to main: the resume check reads the stale non-default value → **parked forever**, only manual `gh pr merge` recovers.
- PR adopted with base=main, later retargeted to a feature branch: guard passes on the stale `main` → `MergePR` merges into the current non-default base → the GH-4872 incident recurs through the guarded path.

Fix: assign `prState.TargetBranch = ghPR.Base.Ref` unconditionally at controller.go:2065 (`ghPR` is already fetched every tick — zero extra API calls).

**2 (MEDIUM). Leg 2's third site missing.** The `handleMerging` post-merge finalize block (~controller.go:3702) still closes/labels-done/completes with no base predicate — GH-4872 explicitly listed it. With fix 1 it's hard to reach; add the same non-default-base predicate + alert there as belt-and-braces (do NOT close the issue / label done / monitor.Complete / self-heal / board→Done when the merge landed off-default; alert + issue comment instead, per the existing scanner-site behavior from PR#4908).

**3 (LOW).** Unresolvable base (empty TargetBranch + `GetPullRequest` failing) holds the PR with only a per-tick Warn — add a one-time alert so the soft-wedge is visible.

**4 (LOW).** `parkForBaseMismatch` reuses the shared `Parked` flag (GH-4596 misconfig parking): a PR parked for a misconfig that later hits base mismatch skips the mismatch alert/comment. Distinguish the park reason (existing `EscalationReason` field) so each cause alerts once.

## Investigation

GH-4415's premise (hypotheses 1/2) was that a PR re-armed via `RestoreState`
after a daemon restart takes a different, *event-driven* code path than a
freshly-registered PR — one that only reacts to a *new* check-run webhook
event, so a check that already resolved (green or red) before the restart is
invisible to it until the 30m `CIWaitTimeout` fires.

Sibling GH-4436 already inspected `RestoreState` (`controller.go:1071`) and
`CIMonitor`'s arm/discovery logic (`ci_monitor.go`) against this hypothesis
and **refuted it**: there is no check-run webhook handler and no event-driven
watcher anywhere in this codebase (confirmed again here — `grep -rn
"check_run\|CheckRunEvent"` across `internal/` matches only test files and
the raw webhook payload type in `internal/adapters/github/types.go`, never a
production handler). CI status is 100% poll-based.

This subtask (GH-4439) independently re-verified the specific claim in its
own scope — that an already-resolved restored PR reaches its terminal
outcome ('released' for green, 'failed' for red) on the very first poll tick
after restart, not after waiting for a websocket/event notification or the
30m timeout:

- `RestoreState` (`controller.go:1071-1130`) does exactly one thing per PR:
  copy the persisted `*PRState` (including `Stage`, e.g. `StageWaitingCI`)
  into `c.activePRs`. It never touches `c.ciMonitor` and never seeds/skips
  any polling state.
- `processAllPRs` (`controller.go:4830`) walks `c.activePRs` on every tick
  and dispatches through `ProcessPR` → the `switch prState.Stage` table
  (`controller.go:1339-1360`) — identically for a PR that entered the map via
  `RestoreState` or via `OnPRCreated`. There is no branch anywhere that
  distinguishes "restored" from "fresh" state.
- For `StageWaitingCI`, that dispatch is `handleWaitingCI`
  (`controller.go:1438`), which calls `c.ciMonitor.CheckCI` →
  `checkStatus` → `ghClient.ListCheckRuns` — a full **current-state** read of
  GitHub's check-runs API, not a diff against previously-seen events. On
  `CISuccess` it sets `Stage = StageCIPassed` immediately
  (`controller.go:1552`), which proceeds toward merge/`StageReleasing`/
  `memory.StageReleased` on subsequent ticks. On `CIFailure` it sets `Stage =
  StageCIFailed` immediately (`controller.go:1559`), which `handleCIFailed`
  processes as a fast failure path (notifies, and either spawns a bounded
  fix cascade or, once the iteration/size guard trips, sets `Stage =
  StageFailed` — `controller.go:1738`) rather than idling until
  `CIWaitTimeout`.
- The post-merge/release leg (`handlePostMergeCI`, `controller.go:2755`)
  follows the identical non-blocking poll-once-per-tick pattern for the
  release-triggering SHA.

### Empirical check

Seeded a `*PRState{Stage: StageWaitingCI, CIWaitStartedAt: <25m ago>}`
directly into `c.activePRs` (bypassing `OnPRCreated` entirely, mirroring
exactly what `RestoreState` does) against a stub GitHub server returning
already-terminal check-runs, then called `c.ProcessPR` once:

- Green check-runs (`conclusion: success`) → `Stage` became `StageCIPassed`
  on that single call. Log: `PR stage transition ... from=waiting_ci
  to=ci_passed`.
- Red check-runs (`conclusion: failure`) → `Stage` became `StageCIFailed` on
  that single call. Log: `PR stage transition ... from=waiting_ci
  to=ci_failed`.

Both resolved on the first tick, ~25 minutes before `CIWaitTimeout` would
have fired, confirming no wait for "the next check-run event" occurs — there
is no such event to wait for; the poll itself is the current-state read.

This scratch test was run locally (`go test ./internal/autopilot/... -run
TestScratch_GH4439 -v`, both subtests PASS) and then discarded rather than
committed: it duplicates the exact scenario sibling GH-4440 is scoped to add
as a permanent regression test
(`internal/autopilot/gh4415_restore_ci_poll_test.go`), and this subtask's
scope fence covers verification, not authoring that test file.

## NO-OP RATIONALE

`internal/autopilot/controller.go:1071` (`RestoreState`) and
`internal/autopilot/controller.go:1438` (`handleWaitingCI`): no source change
required. `RestoreState` only populates `c.activePRs`; the same
`processAllPRs`/`ProcessPR` poll loop that drives fresh PRs drives restored
ones, and `handleWaitingCI`/`handlePostMergeCI` already perform a full
current-state check-runs read on every tick (not an event-diff), so an
already-green or already-red restored PR resolves on the first tick after
restart — exactly the behavior this subtask asked to verify. GH-4415's
"watcher only reacts to new events" premise does not describe any code path
that exists in this repo (independently confirmed here, corroborating
sibling GH-4436's refutation, PR #4443). The real 30m-timeout incident GH-4415
reports has a different root cause outside a code fix in this poll loop
(config/allowlist mismatch or a transient API gap — GH-4415's hypothesis 1/3
territory), which is out of this subtask's scope fence.

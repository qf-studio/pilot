## Problem

GitHub Issue GH-4747: feat(github): GitHub SDK clients resolve tokens per-request so App-token refresh propagates mid-process

## Problem

GH-4743 (PR #4745) scope boundary (2), `sops/config/github-token-architecture.md`: GitHub SDK clients are constructed once at daemon startup with a static token. With App auth active, the installation token expires ~hourly and refreshes in `github.TokenSource` — but already-built clients keep the boot-time token and start failing 401 roughly an hour after start. This makes App auth unusable for the long-lived daemon until fixed; second prerequisite (with the gh-CLI sibling ticket) for the actual cutover.

## Acceptance

1. SDK client construction takes a token *source* (func or interface returning the current token) instead of a static string; each request resolves the token at call time. When app auth is inactive, the source returns the boot-resolved token — zero behavior change.
2. All long-lived client construction sites move to the source (poller, PR/issue clients, autopilot scanners — find them via the construction chokepoint(s), don't scatter).
3. No token value in logs; 401-after-refresh regression covered by a test with a fake source that rotates mid-test.

## Scope fence

No gh CLI changes (sibling ticket) · no auth-mode changes · no client-library swap.

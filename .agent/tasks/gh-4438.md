## Investigation

This subtask depends on two things that turn out not to hold:

1. **The "new shared helper" doesn't exist on `main`.** Sibling GH-4437
   ("extract shared check-runs current-state polling helper") was closed
   `pilot-failed` — its PR #4445 (`CIMonitor.fetchCheckRuns`) never merged
   because CI failed, and the unresolved follow-up (#4446) is still stuck
   in `pilot-needs-clarification`. `grep fetchCheckRuns
   internal/autopilot/ci_monitor.go` returns nothing in this worktree.

2. **The "re-armed waiting_ci watcher" / "30m timer" this task describes
   short-circuiting doesn't exist in the architecture.** Verified directly
   by reading the code (not just citing sibling GH-4436, whose own PR #4443
   also closed unmerged so its memory file didn't survive on `main`):
   - `RestoreState()` (`controller.go:1071`) only copies persisted PR rows
     into `c.activePRs`. No watcher is armed, no timer is started, nothing
     CI-related happens here.
   - `handleWaitingCI()` (`controller.go:1438`) runs uniformly for every PR
     in `StageWaitingCI` on every `processAllPRs` tick, regardless of
     whether the PR was restored or freshly registered — it always calls
     `CIMonitor.CheckCI` → `checkStatus` → `ListCheckRuns` (a genuine
     current-state read) in the same pass where it checks the timeout.
     There's no "listen for new events only" branch to bypass.
   - `CIWaitStartedAt` is persisted/restored by `state_store.go`, not reset
     at restart (GH-4130 already fixed that class of bug), so there's no
     fresh 30m timer starting at restore time either.

Full evidence trail: `.agent/knowledge/memories/learnings/gh4438-restore-ci-poll-noop-confirms-refutation.md`.
A `// Decision:` comment was added at `RestoreState()` (`controller.go:1068`)
pointing future readers at this finding.

## NO-OP RATIONALE

`internal/autopilot/controller.go:1071` (`RestoreState`): no functional
change made. This subtask's fix ("call the new shared helper... before
starting the 30m timer, or short-circuit the timer entirely if checks are
already terminal") targets a helper that doesn't exist on `main` (GH-4437
never merged) and a watcher/timer-start mechanism that doesn't exist in
`RestoreState()` — CI status is already polled uniformly for restored and
fresh PRs on every tick via `handleWaitingCI`/`CheckCI`, and
`CIWaitStartedAt` already survives restarts via persisted state (GH-4130).
Forcing a call to a nonexistent helper, or adding a redundant poll that
duplicates what the very next tick already does (≤ default `CIPollInterval`
later), would be inert at best and risk masking the real, still-unidentified
root cause of the canary incident at worst. Added a `Decision:` comment at
`controller.go:1068` and a Navigator memory entry so sibling subtasks
(#4439-#4442) don't re-spend investigation budget re-deriving this.

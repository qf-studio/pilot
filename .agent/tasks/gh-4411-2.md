## Resolution: NO-OP

**NO-OP RATIONALE:** `internal/approval/slack.go:118-125` (Rehydrate doc comment) —
GH-4411's own text frames this as **mutually exclusive alternatives**:

> Approval requests must survive restart. Either:
> 1. **Rehydrate**: persist pending requests ... and on boot re-arm handlers for
>    every awaiting_approval PR, honoring old buttons' requestIDs; **or**
> 2. **Re-post**: on boot, for each awaiting_approval PR, invalidate the stale
>    Slack message ... and post a fresh approval request.

Subtask 1 (commit `b76a8244`, already on this branch) fully implements Option 1
("Rehydrate") end-to-end and it is the *shipped, tested* fix for the parent bug:

- `PendingApprovalStore` persistence on send (`SendApprovalRequest`)
- `SlackHandler.Rehydrate()` re-arms every `awaiting_approval` request on boot,
  **honoring the original message's requestID** (deliberately, per the code
  comment at `internal/approval/slack.go:118-125`)
- `DecisionRecorder` so a click on a rehydrated request reaches the pipeline
  with no surviving waiter goroutine
- `PruneExpired()` sweep for restart-orphaned timeouts
- Integration test `TestRestartApprovalFlow_Slack_WritesExecutionDecisionAndResumesMerge`
  proving the full restart → click → merge chain

Subtask 2 asks for Option 2 ("Re-post": invalidate the stale message, post a
fresh one). Implementing it now would not be additive — it would **directly
contradict** the design Option 1 already shipped: Option 1's Rehydrate exists
specifically so the *original* Slack message's button keeps working
("Rehydrate deliberately does NOT repost a fresh message: it re-arms the
existing button's requestID in place" — `slack.go:123-125`). Editing that same
message to "expired — see new message" and posting a second one would strip
away the very behavior subtask 1 was built and tested to preserve, for no net
gain: the parent bug (buttons dying on restart, PRs stranding at
`awaiting_approval`) is already resolved by the shipped Option 1 path.

Doing both is not "belt and suspenders" — they are two competing fixes for the
one root cause, and shipping one fully satisfies GH-4411's acceptance bar
(approval buttons survive a daemon restart). No code change made in this
subtask; `go build ./...` and `go test ./internal/approval/... ./internal/autopilot/...`
both pass on the current tree.

# GH-5139

**Created:** 2026-08-23

## Problem

GitHub Issue GH-5139: fix(dispatch): task cancel's re-arm hint is false — reopen/relabel never re-admits a canceled task-id; align behavior or message (GH-5127/5129 recovery)

## Problem

`pilot task cancel` (GH-4678) prints:

> This task will not be re-picked by the dispatcher or poller unless its issue is reopened/relabeled.

That promise is false. Verified live 2026-08-23 (GH-5127/GH-5129 recovery, following the GH-5133 wedge): after cancel, BOTH re-arm verbs the hint names were tried against the running daemon —

1. pilot label removed + re-added (issue open throughout) → next poll: "Skipping re-dispatch — completed execution exists"
2. issue closed + reopened (label intact) → poll tick seconds later: same skip

The poller admission check treats a `canceled` execution row as a terminal completion for the task-id unconditionally; no GitHub-side state affects it. Result: an operator who cancels a wedged task (exactly what the cancel verb is FOR — see the GH-5133 incident) can never re-run the same issue. The only recovery is superseding with a fresh issue number (done for #5127→#5137, #5129→#5138), which loses issue history/links and surprises humans.

## Decide + fix (implementer picks ONE, with the reasoning recorded)

- **Option A (align behavior to the hint)**: make deliberate re-arm work — the admission check ignores `canceled` rows when the issue currently carries the trigger label AND the cancel predates the label's most recent add (or the issue was closed+reopened after cancel). Guard against the original GH-4655 problem: this must be an explicit operator gesture, not an automatic retry loop — the existing repick-backoff and hard-cap machinery must still apply to the re-armed generation.
- **Option B (align the hint to behavior)**: cancel is truly permanent per task-id; fix the CLI message to say "permanently; to re-run, file a new issue", and have cancel post an issue comment stating that. Cheaper, but leaves no in-place recovery for the cancel-to-unwedge flow that the GH-5133 incident showed is real.

Option A is the one that matches operator intuition and the incident playbook; pick B only if A's claim-generation interaction turns out genuinely unsafe.

## Acceptance

1. Whichever option: the CLI message, the actual admission behavior, and the SOP/troubleshooting-table row for cancel (`.claude/skills/pilot-aws/SKILL.md` quick table + any `.agent/sops` mention) all agree with each other.
2. Option A: integration-style test — cancel, relabel, next admission tick dispatches a fresh generation-0 execution; the re-armed task still honors repick backoff/caps.
3. Option B: cancel posts the permanence comment on the issue; message updated.

## Decision

**Chose Option A** (align behavior to the hint) — matches operator intuition and the
GH-5127/5129/GH-5133 incident playbook; no evidence surfaced during implementation that
the claim-generation interaction is unsafe, so Option B was not needed.

Implementation:

- `terminalCompletionChecker` (`cmd/pilot/main.go`), the earliest live admission gate
  for the GitHub SDK poller, gained `ghClient`/`repoOwner`/`repoName`/`triggerLabel`
  fields (nil/zero-value by default — every pre-existing constructor, including all
  prior tests, keeps the old "canceled is permanent" behavior byte-for-byte).
- When `HasTerminalCompletion` reports `done=true` off a `canceled` row (not a
  completed/no_op row) and a GitHub client is wired, `tryRearmCanceled`
  (`cmd/pilot/rearm_canceled.go`) probes GitHub: issue must be open + carry the
  trigger label right now, AND the issue-events timeline
  (`GET /issues/{n}/events`) must show a `reopened` or matching `labeled` event
  timestamped strictly AFTER the cancel's `completed_at`. Merely "still open/labeled"
  is insufficient by design — this is what keeps the re-arm an explicit, timestamped
  operator gesture rather than an accidental/automatic one (the GH-4655 guard).
- On a positive probe, the canceled row is demoted to `status='failed'`
  (`Store.ReclassifyCanceledForRearm`, mirroring the existing
  `ReclassifyCompletionAsFailed` "demote don't delete" idiom) rather than deleted or
  claim-generation-hacked. This routes the re-armed task through the *existing*,
  unmodified `nextRetryGeneration` retry-with-backoff/hard-cap machinery — no bespoke
  bypass of those invariants.
- A negative probe (or probe error) arms `repickBackoff.recordClaimLostDrop`, so a
  canceled-but-not-yet-relabeled task pays for at most one GitHub API round trip per
  backoff window, not one per ~30s poll tick (mirrors the GH-4469 throttling fix this
  gate already relies on).

**Deviation from the literal acceptance text:** AC2 says "next admission tick
dispatches a fresh generation-0 execution." `execution_claims` rows are explicitly
documented as permanent per `(task_id, project_path, generation)` and never reused —
a literal claim-generation 0 replay is not how any other retry path in this codebase
works either. Read "generation-0" as loose phrasing for "a genuinely fresh
execution" and implemented it as the normal next integer generation
(`priorGeneration + 1`) via the existing retry path, consistent with every other
post-failure retry in the system.

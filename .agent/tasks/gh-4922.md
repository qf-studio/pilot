# refactor(dashboard,gateway): drop the TUI eval panel — export eval pass@1 via the Prometheus endpoint instead

## Problem

The TUI eval stats panel (`renderEvalStats`, `internal/dashboard/tui.go:2439`) rendered for the first time on 2026-08-17 when the first-ever `eval_tasks` row landed (PR#4920 merge). Operator decision: eval pass@1 belongs in the Prometheus surface with the other pipeline metrics (`pilot_prs_merged_*`, `pilot_build_info`), not as an extra dashboard card. One metrics surface, no bespoke TUI panel.

## Scope

1. **Remove the TUI panel**: delete `renderEvalStats` and its call site in `internal/dashboard/tui.go`, plus the associated assertions in `internal/dashboard/tui_test.go` (~line 1585). No other TUI changes.
2. **Export via the existing hand-rolled exporter** (`internal/gateway/prometheus.go`, same writeHelp/writeType/write* idiom):
   - `pilot_eval_tasks_total{success="true|false"}` — gauge, row counts from `eval_tasks` across all projects (fleet scope, matching the GH-4830 default).
   - `pilot_eval_pass_ratio` — gauge in [0,1], fraction of `eval_tasks` rows with `success=1`. Omit both metrics (or emit 0 with a HELP note) when the table is empty — pick one and document it in HELP text.
3. **Leave collection untouched**: the `handleMerged` eval-extraction leg (`internal/autopilot/controller.go:4413`, GH-2059) and the `eval_tasks` schema stay exactly as they are. The eval regression alert (`internal/alerts`) stays as-is.

## Scope fence

- No changes to eval extraction, `eval_results`, the eval runner, or alert rules.
- No new dashboard panels anywhere (TUI or grafterm config) — metric export only.
- Do not touch the metrics-scope machinery from GH-4830/GH-4832.

**This task must NOT be decomposed — implement as a single PR.** <!-- pilot:no-decompose -->

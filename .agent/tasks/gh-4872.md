# GH-4872

**Created:** 2026-08-17

## Problem

GitHub Issue GH-4872: fix(autopilot): stacked PR auto-merged into its non-default base and finalized as delivered — false-success + content-loss window

> Re-anchored 2026-08-17 against pilot main@3ae95770 (all file:line refs verified by code research). SDK leg (poller done-check) is filed separately on qf-studio/studio-sdk and cross-linked below — this issue covers the pilot-side legs only.

## Incident (2026-08-15, TASK-478 UI-12)

ui PR#76 was stacked on `pilot/GH-70`. Autopilot squash-merged it **into that stack branch** (merge commit 55e8fb7 = pilot/GH-70's new head), closed issue #71 as delivered, and deleted `pilot/GH-71`. Main had no merge event and none of the content. The stack branch was later deleted during PR#74 cleanup, orphaning the content entirely. Retry was self-sealing: the poller saw "already has merged PRs" and re-marked the issue done. Recovery required abandoning ui#71 and filing fresh ui#83. False-success + content-loss, end to end.

## Root cause

Nothing in the merge→finalize→retry chain ever compares a PR's base ref against the default branch:

- **Merge**: `AutoMerger.MergePR` (`internal/autopilot/auto_merger.go:52`) and its caller `handleMerging` (`controller.go:3602`→`:3647`) gate on breaker/CI/attempts only. `prState.TargetBranch` is populated (`controller.go:2065`, from `ghPR.Base.Ref`) but never read at merge time. `CanMerge` (`auto_merger.go:171`) checks Merged/closed/Mergeable only. Adoption ignores base too: `ScanExistingPRs` (`controller.go:6210`) and `reconcileOrphanPRs` (`:6297`) filter only on the `pilot/GH-` head prefix.
- **Finalize**: the `handleMerging` post-merge block (`controller.go:3702-3760`) closes the issue, labels done, `monitor.Complete`, self-heals the execution row, board→Done — no base predicate. Same for the scanner: `ScanRecentlyMergedPRsWithWindow` checks `pr.Base.Ref != c.resolveMainBranchName()` for HUMAN PRs only (`controller.go:6541`); the `isPilotPR` path (`:6533-6545`, `:6562-6645`) fires the full delivered pipeline on any merged flag. Store-level self-heal (`internal/memory/store.go:2369/2388`) takes no branch input.
- **Branch cleanup**: four `DeleteBranch` sites (`controller.go:3766`, `:5911` via `removePR`, `:7393`, `:3217`) delete on branch name alone; none checks whether the branch is the BASE of other open PRs (that's how the stack parent's deletion orphaned the merged content).

The only existing base-aware logic, `guardReleaseSHAReachable` (`controller.go:5240`), runs release-side — after merge and issue-close already happened — and its own doc comment names this exact incident class.

## Wanted (pilot legs)

**1. Auto-merge guard: base == default branch or don't merge.**
In `handleMerging` before `MergePR` (or inside `CanMerge`): if `prState.TargetBranch != c.resolveMainBranchName()` (`controller.go:4534` — config-sourced, warns + falls back "main"), do NOT merge. Park the PR with the existing escalation idiom (comment on the PR naming the base mismatch once, alert, `awaiting_approval`-style hold) — a non-default base under autopilot means a stacked or mis-based PR; a human must decide (retarget vs merge the stack in order). If `TargetBranch` is empty at that point, re-read the PR rather than fail open.

**2. Delivered-finalize requires default-branch landing.**
Same predicate at every site that converts "PR merged" into "issue delivered": the `handleMerging` finalize block, the `isPilotPR` scanner path (mirror the human-PR check at `controller.go:6541`), and `checkExternalMergeOrClose`'s finalize. A PR merged into a non-default base must NOT close the issue / label done / `monitor.Complete` / self-heal to completed / board→Done — instead alert + leave the issue retryable (comment on the issue that content merged sideways into <base>).

**3. External-finalize double-fire.**
`checkExternalMergeOrClose` (`controller.go:7163`) guards ScopeKey/StagePostMergeCI/StageReleasing but NOT `StageMerged`, and it runs BEFORE `ProcessPR` in `processAllPRs` (`:7058` vs `:7085`). Confirmed sequence for every autopilot-merged PR: tick N `handleMerging` finalizes and leaves `Stage = StageMerged`; tick N+1 the external branch re-runs every side effect — second `UpdateIssueState(closed)`, second merge-completion comment (the `MergeNotificationPosted` guard used at `:3734` is absent at `:7218`), second `recordExecutionEvent(StageMerged)` (PR#4870 block, `:7280-7296`; `recordExecutionEvent` has no idempotency key), second `DeleteBranch` via `removePR`. Add `StageMerged` to the guard list, apply the `MergeNotificationPosted` guard to the external comment, and extend `TestCheckExternalMergeOrClose_StageGuards` (`controller_release_cycles_test.go:840`) to pin it.

**4. Branch-delete guard: never delete a branch that is the base of open PRs.**
Before any of the four `DeleteBranch` sites fires (cheapest: one guard helper they all call), list open PRs and skip deletion when the branch is some PR's `Base.Ref` — log + alert instead. `ListPullRequests` has no `base=` filter, but the decoded PR struct carries `Base`; client-side filter over open PRs is sufficient at our PR counts.

## Acceptance

- A `pilot/GH-*` PR whose base is not the default branch: never auto-merged (parked + alerted, PR comment posted exactly once); if merged externally anyway, its issue is NOT closed/done/self-healed and an alert fires.
- Autopilot-merged PR produces exactly one issue-close, one completion comment, one terminal `StageMerged` execution event, one branch delete across subsequent ticks (test drives two ticks).
- A branch that is the base of an open PR survives all cleanup paths (test seeds a stacked pair).
- Table-driven tests for the new predicates; existing merge-path tests (`auto_merger_test.go`, `controller_merge_test.go`) extended with a non-default-base case each.
- `make test` green.

# GH-4384

**Created:** 2026-07-17

## Problem

GitHub Issue GH-4384: fix(autopilot): CI watcher polls legacy combined-status API while discovery uses check-runs — every Actions-only new repo times out at waiting_ci with green checks

## Context

**Every PR on a newly-onboarded repo dies at `waiting_ci` with "CI timeout after 30m0s" while its checks are green.** Observed on qf-studio/pointer (onboarded 2026-07-16, first cycle): PRs #5/#6/#7 all followed `pr_created → waiting_ci → "CI checks discovered" (checks=[go] / [web]) → 30m timeout → failed`, ledger `ci_status` frozen at `pending`, `gh pr checks` shows pass on all three (PR #7's check completed ~1 min into the watch — not a stale-SHA race). The Slack pre_merge approval never fires because the pipeline dies first. Same daemon merges qf-studio/pilot PRs normally all day.

**Root-cause evidence (2026-07-16 20:0xZ, PR #7 head `35e110afb568f91805528ebd7e6abedda46a8524`):**

```
GET repos/qf-studio/pointer/commits/{sha}/check-runs → go: status=completed conclusion=success
GET repos/qf-studio/pointer/commits/{sha}/status     → state=pending total_count=0
```

GitHub's legacy combined-status API returns `state=pending` when ZERO commit statuses exist, and GitHub Actions only writes check-runs, never legacy statuses. So: **discovery reads the check-runs API (finds [go]) but the completion watcher polls the legacy combined-status API → phantom "pending" forever.** Established repos don't hit it because non-empty `required_checks` (e.g. pilot's [test, lint]) routes the watch down the check-runs path (see GH-4333→#4342 precedence handling); pointer has no `required_checks`, `ci_checks.mode: auto` — discovery succeeds, watch goes blind.

Ledger rows: `autopilot_pr_state` (5,6,7 × qf-studio/pointer) stage=failed, ci_status=pending, error="CI timeout after 30m0s", created 15:41Z/16:06Z/19:03Z.

Note: an unrelated transient DNS outage (`lookup api.github.com: no such host`, 15:16–15:18Z) appears in the same day's log — it does NOT overlap PR #7's watch window; do not chase it.

Single concern, **do not decompose**. <!-- pilot:no-decompose -->

## Approach

1. In the autopilot CI watcher, unify the completion check with the discovery source: when checks were discovered via the check-runs API (auto mode), completion MUST be evaluated from check-runs conclusions for the discovered names — never the legacy combined-status endpoint. Treat `combined status total_count==0` as "no signal", not "pending".
2. Audit the `required_checks`-empty + `ci_checks.mode: auto` path end-to-end (discovery grace → watch → conclusion) — the #4342 precedence fix covered required-checks resolution; this is the observation side of the same split.
3. Regression test: fake GitHub returning check-runs=[go: completed/success] + combined-status={pending, total 0} → watcher must conclude success, not timeout. Inverse case (a repo genuinely using legacy statuses only) must still work.

## Acceptance

- A repo with zero `required_checks`, `ci_checks.mode: auto`, and Actions-only CI advances `waiting_ci → ci_passed` when its discovered check-runs complete (table-driven, both APIs faked).
- `total_count==0` combined status is never interpreted as pending.
- Existing pilot-repo path (required_checks non-empty) untouched — its tests still pass.
- `make build/test/lint` green.

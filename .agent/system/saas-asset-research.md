## Asset: pilot-tenancy
Pilot is a single-binary Go daemon designed around one operator, one machine, one home directory. Startup: `pilot start` (cmd/pilot/main.go, cobra) loads `~/.pilot/config.yaml` (internal/config/config.go: Load → DefaultConfig + YAML overlay + os.ExpandEnv with GH-3755 guard that errors if a ${VAR} on a token/key/secret line is unset). Config is one flat file holding gateway host/port (default 127.0.0.1:9090), auth, all 10 adapter blocks (credentials inline or via ${ENV}), orchestrator/autopilot, executor backend, memory path, budget, approval, tunnel, and a `projects:` list — each project = local filesystem path + GitHub owner/repo + per-project quality/release overrides. Per-repo overrides come from `.pilot/workflow.yaml` in the target repo (internal/executor/workflow, TASK-304: max_turns etc.). Hot reload exists only as Config.Reload() used after self hot-upgrade (GH-879); adapters/pollers are wired once at startup from config, so credential/integration changes effectively require restart. State: SQLite via modernc.org/sqlite (pure Go, CGO-free — container friendly) at `~/.pilot/data/pilot.db`, WAL, MaxOpenConns(1). Schema (memory/store.go): executions (task queue + results + tokens/cost/model/effort columns), patterns + cross_patterns/pattern_projects/pattern_feedback (learning), usage_events (already has user_id/project_id/unit_cost — proto-billing), sessions, autopilot_metrics, execution_logs, approval_pending, execution_events, eval_*, memories (knowledge.go). Gateway (internal/gateway): one http.Server with /ws (control-plane WebSocket: ping/task/status/progress messages, SessionManager broadcast), /ws/dashboard, REST /api/v1/* (status, tasks, autopilot, metrics, queue, history, logs, gitgraph), /health /ready /live /metrics (Prometheus), and HMAC/Ed25519-verified webhook endpoints for 7 trackers. Auth is weak: type "claude-code" = accept any localhost connection; type "api-token" = single static bearer token; auth wraps only /api/v1/*, not /ws. Inbound webhooks reach the laptop via internal/tunnel (cloudflared/ngrok CLI wrappers). Execution: git worktrees in os.TempDir() (`/tmp/pilot-worktree-<task>-<nano>`, pool at fixed `/tmp/pilot-worktree-pool-N` — collides across instances sharing a host), spawns `claude -p --dangerously-skip-permissions` (or opencode/qwen-code/raw Anthropic/OpenAI-compatible backends via backend_factory.go), shells out heavily to `gh` and `git` CLIs (creds from GITHUB_TOKEN env / gh auth / ambient git credential helper). Claude auth is ambient (~/.claude or ANTHROPIC_API_KEY). Human surfaces: bubbletea TUI dashboard, an embedded React web dashboard (build tag embed_dashboard, served at /dashboard/), Telegram/Slack/GitHub approval handlers (internal/approval: pre_execution/pre_merge/post_failure stages persisted in approval_pending, survive restarts).
**Reusable:** 
- Executor backend abstraction (internal/executor/backend.go, backend_factory.go): 5 backends — claude_code CLI, opencode, qwen_code, anthropic API, openai-compatible (api_base_url + api_auth_token covers OpenRouter/BYOK) plus model_routing/effort_routing config — directly reusable as the SaaS 'models management' engine
- Approval package (internal/approval): channel-agnostic Handler interface + persisted approval_pending table + DecisionRecorder that survives daemon restarts (GH-3825) — a dashboard approval UI is just one more Handler implementation
- Gateway webhook layer (internal/gateway/server.go): signature-verified webhook handlers for GitHub (HMAC-SHA256), Linear (Ed25519), GitLab, Jira, Asana, AzureDevOps, Plane — reusable as the SaaS ingestion edge
- usage_events table + internal/memory/metering.go: already models user_id/project_id/event_type/unit_cost/total_cost per execution — seed of per-tenant metering/billing
- execution_events + execution_logs + Prometheus exporter (internal/gateway/prometheus.go, /metrics) — per-customer logs/monitoring feed exists; just needs tenant labeling
- Embedded React dashboard (cmd/pilot/embed_dashboard.go → /dashboard/ SPA) + /ws/dashboard live stream + /api/v1/{metrics,queue,history,logs,gitgraph} — a working per-instance web UI contract the SaaS dashboard can consume per-instance
- Worktree isolation + pool + orphan cleanup (internal/executor/worktree.go) — battle-hardened per-task git isolation incl. OOM-orphan reclamation (GH-2168)
- Config schema (internal/config/config.go) as the de-facto 'instance spec': the SaaS control plane can render exactly this YAML per tenant and ship it to the instance — env-var expansion with sensitive-key validation already built in
- modernc.org/sqlite (CGO-free) — the binary containerizes trivially; `pilot start` flags already allow headless mode (--no-gateway, adapter toggles)
- Health endpoints /health /ready /live with ReadinessChecker interface — ECS/K8s probe-ready today
**Gaps:** 
- No multi-tenancy anywhere: one config file, one SQLite DB keyed by project_path (local FS paths), no tenant/org ID in any table except the unused user_id in usage_events; TeamConfig (GH-635) is a single team_id + member_email scoping knob, not tenancy
- No remote control plane: the /ws WebSocket is inbound-only (dashboard/control clients connect TO the daemon); there is no outbound 'phone home' connection from instance to a central service, no instance registration, no remote config push — Reload() is only invoked after self-upgrade, and adapters are wired once at startup (credential change = restart)
- Auth is not SaaS-grade: claude-code auth = trust all localhost; api-token = one static shared bearer; /ws is not behind the auth middleware; no OAuth/OIDC/JWT — integration with auth-service must be built
- Repos are assumed pre-cloned on local disk (ProjectConfig.Path); no clone-on-provision, no git credential injection (relies on ambient gh auth / credential helper / GITHUB_TOKEN env), no GitHub App installation-token flow (config comment mentions 'GitHub App token' but code takes a static string)
- Claude Code auth is ambient per-machine (~/.claude session or ANTHROPIC_API_KEY env) — per-tenant key isolation/injection for hosted instances doesn't exist
- Fixed shared paths break multi-instance-per-host: /tmp/pilot-worktree-pool-0..N is index-named per instance (collision), CleanupOrphanedWorktrees scans all /tmp/pilot-worktree-* (it does skip worktrees whose gitdir points at another repo, but two instances on the SAME repo would reap each other), gateway default port 9090, single ~/.pilot dir
- No kanban/board model: executions table is a queue, not a board; no external-issue↔internal-card mapping or bidirectional sync state (adapters are poll/webhook→task ingest, write-back is status comments/labels only)
- Webhook ingress assumes a tunnel (cloudflared/ngrok CLI) — hosted instances need real ingress + per-tenant webhook routing/secret management
- No API to create/configure integrations at runtime; onboarding is interactive CLI wizards (pilot setup / pilot onboard / project_wizard.go)
**Risks:** 
- Executor runs `claude --dangerously-skip-permissions` and shells out to git/gh with the instance's ambient credentials — on shared infra this is remote-code-execution-as-a-service; each tenant needs a VM/container boundary (one instance per tenant, never shared), which matches the aws-infrastructure plan but must be treated as a hard security invariant
- Config file contains all secrets in plaintext YAML (0600) — Save() writes tokens back to disk; moving to SaaS needs a secrets backend or env-only injection, and Save() round-trips would leak pushed secrets to instance disk
- SQLite MaxOpenConns(1) + WAL is fine per instance but means the SaaS dashboard cannot query instance state directly at scale — needs an event/metrics export path (execution_events + Prometheus exist) rather than DB access
- Heavy external-binary surface per instance: claude CLI, gh, git, optionally cloudflared/opencode/qwen — image build + version pinning becomes part of the product; self hot-upgrade (UpgradeConfig.AutoHotUpgrade default true, PILOT_RESTARTED re-exec) conflicts with immutable fleet images and should be disabled in hosted mode
- gateway websocket /ws has message types but near-zero implemented control semantics (router.go registers only ping by default) — 'central control plane over existing WS' is mostly aspiration, not asset; budget for a new agent/instance protocol
- Founder's questionable item (models management): the multi-backend engine is real and cheap to expose (config enum + api_base_url/api_auth_token), but non-Claude backends get far less battle-testing in this codebase (claude_code is the default and the only path exercised by the project's own dogfooding) — recommend shipping BYO-Anthropic-key + curated Claude models first, defer OpenAI-compatible/OpenRouter to a later tier
**Key facts:** 
- Config: ~/.pilot/config.yaml (config.DefaultConfigPath), full example configs/pilot.example.yaml (685 lines); Load() expands ${ENV} and hard-fails on unset env refs under keys matching token|key|secret|password; per-repo override file: .pilot/workflow.yaml in the target repo
- Gateway defaults 127.0.0.1:9090; routes: /ws, /ws/dashboard, /api/v1/{status,tasks,autopilot,metrics,queue,history,logs,gitgraph}, /webhooks/{linear,github,gitlab,jira,asana,azuredevops,plane}, /health /ready /live /metrics, /dashboard/ (embedded React SPA, build tag embed_dashboard)
- Gateway auth (internal/gateway/auth.go): AuthTypeClaudeCode accepts any RemoteAddr prefixed 127.0.0.1/localhost/[::1]; AuthTypeAPIToken = single static bearer with constant-time compare; middleware applied only to /api/v1/*
- WS protocol (internal/gateway/router.go): JSON {type,payload}, types task/status/progress/ping/pong; only ping handler registered by default; SessionManager supports Broadcast — no instance-to-cloud outbound dial exists
- SQLite: modernc.org/sqlite (no CGO) at <memory.path>/pilot.db (default ~/.pilot/data), WAL + busy_timeout 10s + MaxOpenConns(1); key tables: executions (queue+results, token/cost/model columns), usage_events(user_id,project_id,event_type,total_cost), approval_pending, execution_events, cross_patterns learning set, memories (knowledge graph in internal/memory/knowledge.go + graphrecall/)
- Adapter credentials are YAML fields (github.token, gitlab.token, azuredevops.pat, jira.{base_url,username,api_token}, linear.api_key, asana.access_token, plane.api_key, slack.{bot_token,app_token,signing_secret}, telegram.{bot_token,chat_id,allowed_ids}) typically set to ${GITHUB_TOKEN} etc.; cmd/pilot also reads GITHUB_TOKEN, ANTHROPIC_API_KEY, SLACK_BOT_TOKEN, LINEAR_API_KEY, OPENAI_API_KEY env directly
- Executor backends (executor.BackendConfig.Type): claude_code (default; spawns `claude -p --dangerously-skip-permissions --output-format stream-json`), opencode, qwen_code, anthropic (raw API), openai (api_base_url + api_auth_token → OpenRouter/BYOK); plus effort_routing, model_routing, intent_judge, decompose, worktree_pool_size knobs
- Worktrees: filepath.Join(os.TempDir(), "pilot-worktree-<taskID>-<unixnano>") per task; pool uses fixed /tmp/pilot-worktree-pool-<index> based on origin/main; CleanupOrphanedWorktrees at startup reaps all /tmp/pilot-worktree-* belonging to this repo (skips other repos' worktrees and pool dirs); heavy JS worktrees observed at 800MB+ each (GH-2168)
- One daemon serves N projects (config projects[] with local paths + github owner/repo + per-project quality/release/canary overrides); orchestrator.max_concurrent default 2; execution modes sequential/parallel/auto with scope-overlap guard
- Single-operator surfaces to replace: bubbletea TUI (internal/dashboard, incl. 'u' keypress upgrade), interactive CLI wizards (pilot setup/onboard/init/project wizard, $EDITOR-based `pilot config edit`), Telegram approval buttons (single chat_id + allowed_ids), Slack/GitHub approval handlers, daily brief to Slack/email, self hot-upgrade re-exec (PILOT_RESTARTED=1)
- Approval flow (internal/approval): stages pre_execution/pre_merge/post_failure, rule-based triggers, PreferredChannel routing, decisions persisted via PRStateWriter into executions so post-restart button taps still land (GH-3825) — clean seam for a web-dashboard approval channel
- Webhook ingress today relies on internal/tunnel (cloudflared or ngrok CLI, macOS service management) because the daemon sits on a laptop; pollers exist as the no-tunnel alternative for all trackers (cmd/pilot/poller_*.go, GitHub via studio-sdk poller unconditionally since GH-4170)

## Asset: auth-service
auth-service (Go 1.25, Gin, module github.com/qf-studio/auth-service) is a dual-port OAuth 2.1 service: public :4000, admin :4001 (no auth on admin — network-isolated by design), gRPC :4002. Postgres 16 (pgx pool) + Redis 7; 15 golang-migrate migrations embedded (migrations/embed.go) with cmd/migrate. Tokens: qf_at_ JWT access (ES256/EdDSA, JWKS at /.well-known/jwks.json, revocation blocklist in Redis), qf_rt_ opaque refresh (only HMAC signature stored in Redis), qf_ak_ API keys, Argon2id+pepper passwords, DPoP support, per-IP rate limiting.

Multi-tenancy is schema-complete but NOT wired end-to-end. Migration 000015 creates a tenants table (uuid id, unique slug, JSONB config for per-tenant password policy/MFA enforcement/allowed OAuth providers/token TTLs, active|suspended|deleted status, seeded Default tenant 00000000-...-0001), adds NOT NULL tenant_id + tenant-scoped unique constraints + composite indexes + Postgres RLS policies keyed on current_setting('app.current_tenant_id') to 14 tables. middleware/tenant.go resolves tenant by subdomain (acme.auth.quantflow.studio), X-Tenant-ID header, or both, with TTL cache and active check. internal/admin/tenant_service.go + storage/tenant_repository.go implement full CRUD, and admin_router.go defines /admin/tenants (GET/POST/PATCH/DELETE). HOWEVER, cmd/server/main.go never instantiates TenantMiddleware, never sets AdminServices.Tenants (so /admin/tenants routes are skipped at runtime), no TenantResolver implementation exists, and no code ever executes set_config('app.current_tenant_id') — RLS is inert. Services read tenant via domain.TenantIDFromContext which returns uuid.Nil, and repos filter WHERE tenant_id=$2 with that nil UUID.

Dual client model is real: ClientType user/service/agent; machine auth via POST /auth/token grant_type=client_credentials (client_id+secret) or X-API-Key qf_ak_ keys (middleware falls through to Bearer, synthesizes service claims with scopes+rate limit; rotation endpoint exists). Both are wired — good fit for per-customer Pilot instances. Human auth today is password POST /auth/login (+TOTP MFA challenge) returning tokens directly; the OAuth 2.1 authorization-code+PKCE and OIDC endpoints (/oauth/authorize, /oauth/token, discovery, userinfo) are handler shells around an OIDCProviderService interface that is nil in main.go ("registered in a subsequent issue") — routes not registered, so no SPA auth-code flow and no OIDC federation today. Sessions use an in-memory store (single-instance only).

Also nil/unimplemented in main.go despite code scaffolding: SAML SP+IdP admin (no internal/saml package), Hydra-style consent flow, agent credential broker/vault, client approval, OAuthAccountRepository (passed nil, so Google/GitHub/Apple social-login providers are implemented and route-wired but account persistence is unwired). MFA TOTP+backup codes fully wired; WebAuthn code exists but is not routed. RBAC: Casbin sub/obj/act with role hierarchy, pg adapter, RequireRoles/RequireScopes(all-of)/RequireClientType middleware, but only 4 fixed global roles (admin/user/service/agent) — no org-level owner/admin/member, and rbacSvc is only used by gRPC CheckPermission. Deployment: single-host docker-compose (production/staging) behind Caddy, GH Actions SSH deploy to one DEPLOY_HOST; staging workflow disabled. README's "v0.67.0 feature-complete, all three phases shipped" overstates reality.
**Reusable:** 
- Token service (internal/token/service.go): ES256/EdDSA JWT access tokens qf_at_, opaque qf_rt_ refresh with Redis-stored signatures, revocation blocklist, DPoP binding — production-quality, reusable as-is
- Client-credentials + qf_ak_ API key path for Pilot instances: internal/admin/apikey_service.go (create/rotate/revoke, scoped, rate-limited, hash-only storage) + internal/middleware/apikey.go (X-API-Key with Bearer fallthrough)
- Tenant data model + isolation schema: migrations/000015_multi_tenancy.up.sql (tenants table, tenant_id on 14 tables, tenant-scoped uniques, RLS policies) and domain/tenant.go per-tenant JSONB config (password policy, MFA enforcement, OAuth provider allowlist, token TTLs)
- Tenant admin CRUD: internal/admin/tenant_service.go + internal/storage/tenant_repository.go + internal/api/admin_tenant_handlers.go — complete, tested, just needs wiring in cmd/server/main.go
- Tenant resolution middleware: internal/middleware/tenant.go — subdomain/header/both modes with TTL cache; needs a TenantResolver impl (trivial: wrap tenant_repository.FindBySlug)
- Admin API on :4001 (internal/api/admin_router.go): users (CRUD, lock/unlock, bulk ops, MFA reset), clients (CRUD, secret rotation), apikeys, webhooks (+deliveries/retry/test), token introspection, metrics (JSON + Prometheus at /admin/metrics/prometheus)
- gRPC AuthService on :4002 (proto/auth/v1): ValidateToken, GetUser, CheckPermission, IntrospectToken — ready for other SaaS services (billing, logs, kanban backend) to validate tokens without OIDC
- Scope enforcement middleware: internal/middleware/rbac.go RequireRoles / RequireScopes (all-of) / RequireClientType; Casbin RBAC engine in internal/rbac with pg adapter (tenant_id column already on casbin_policies)
- Social login providers Google/GitHub/Apple (internal/oauth/, tested, route-wired) with HMAC state manager and PKCE helpers
- Security/ops middleware stack: CORS, correlation IDs, security headers, per-IP rate limiting with lockout, request-size limits, HIBP breached-password check, audit log pipeline (migration 000011, tenant-scoped)
- Hardened single-host deployment templates: deployments/docker-compose.production.yml (read-only container, no-new-privileges, localhost-bound ports), Caddyfile, GH Actions deploy-production.yml with rollback-on-failed-healthcheck
**Gaps:** 
- OIDC provider is not implemented — internal/api/oidc_handlers.go delegates to OIDCProviderService which is nil in cmd/server/main.go, so /oauth/authorize, /oauth/token, discovery and userinfo are unregistered. No authorization-code+PKCE flow exists for the dashboard SPA and no OIDC federation for other services. This is the single biggest build item.
- Multi-tenancy is not wired: TenantMiddleware never applied, no TenantResolver implementation, AdminServices.Tenants never set (tenant admin API dead at runtime), and app.current_tenant_id GUC never set so Postgres RLS never fires. Services pass uuid.Nil tenant into queries.
- No tenant self-service signup/provisioning: tenants are created only via unauthenticated admin API on :4001; SaaS needs a signup -> create-tenant -> create-owner flow and an authenticated control plane in front of :4001 (which currently has zero auth, only correlation-ID middleware).
- No org-level RBAC: roles are 4 fixed strings (admin/user/service/agent) validated in domain/role.go; no owner/admin/member org roles, no invitations, no per-tenant role management API. Casbin model supports hierarchy but policies/enforcer are not tenant-aware in practice and rbacSvc is only exposed over gRPC CheckPermission.
- Session store is in-memory (session.NewMemoryStore in main.go) — breaks with >1 replica; needs the Redis-backed store.
- SAML SSO, consent flow, agent credential broker/vault, client-approval workflow: domain types, migrations (000013, 000014), repos and handlers exist but services are nil in main.go; no internal/saml package at all.
- Social-login account persistence unwired: oauth.NewService receives nil OAuthAccountRepository in main.go despite storage/oauth_repository_pg.go existing; WebAuthn code (internal/mfa/webauthn.go) is not routed.
- Deployment is single-host docker-compose over SSH; no AWS/multi-instance story, staging deploy workflow disabled; Postgres health checker absent from health service (only Redis checker registered).
**Risks:** 
- README claims 'v0.67.0 feature-complete, all three phases shipped' but main.go wiring shows Phase 2 (OIDC provider) and most of Phase 3 (multi-tenancy wiring, SAML, broker, consent) are scaffolding — architecture decisions must be based on the code, not the README. This repo is itself Pilot-built, so handler/service/repo layers exist with tests while integration wiring lags.
- Runtime tenant behavior is likely broken today: with no tenant middleware, register/login pass uuid.Nil tenant_id into FK-constrained inserts and WHERE clauses; unit tests inject tenant IDs explicitly so this gap is invisible in CI. Budget integration testing when wiring tenancy.
- Admin port :4001 relies entirely on network isolation (explicit comment in admin_router.go: 'no auth, no rate limiting'); exposing tenant/user management to a SaaS dashboard requires building an authenticated admin plane — do not proxy :4001 directly.
- Postgres RLS policies exist but the app connects as (presumably) the table-owning role and never sets app.current_tenant_id; RLS does not apply to table owners without FORCE ROW LEVEL SECURITY — isolation currently rests solely on per-query WHERE tenant_id filters once tenancy is wired.
- In-memory tenant cache (middleware/tenant.go) and in-memory sessions both assume a single process; tenant suspension won't propagate across replicas until TTL expiry or a shared cache is introduced.
- No refresh-token rotation visible for SPA use and refresh tokens live only in Redis — Redis loss logs out all users and revocation lists vanish; evaluate persistence before multi-tenant production.
**Key facts:** 
- Ports: public :4000, admin :4001 (unauthenticated, network-isolated), gRPC :4002 (ValidateToken/GetUser/CheckPermission/IntrospectToken). Config via env vars (internal/config/config.go); required: APP_ENV, POSTGRES_*, REDIS_HOST, JWT_PRIVATE_KEY_PATH, SYSTEM_SECRETS, PASSWORD_PEPPER, CORS_ALLOWED_ORIGINS.
- Tenant = row in tenants table: uuid id, unique slug (used as subdomain label, e.g. acme.auth.quantflow.studio with TENANT base-domain config), JSONB config (password policy, MFA required/methods/grace, allowed OAuth providers, access/refresh TTL overrides), status active|suspended|deleted; seed Default tenant 00000000-0000-0000-0000-000000000001. Resolution modes: subdomain | header (X-Tenant-ID) | both (subdomain wins).
- Admin API on :4001 (route tree in internal/api/admin_router.go): /admin/tenants, /admin/users (+bulk lock/unlock/suspend/assign-role, MFA reset), /admin/clients (+rotate-secret, approve), /admin/apikeys (+rotate), /admin/webhooks (+deliveries, retry, test), /admin/credentials (broker, unwired), /admin/saml/idps (unwired), /admin/tokens/introspect, /admin/metrics{,/prometheus}, Hydra-style /admin/oauth/auth/requests/{login,consent} (unwired). Pagination: page/per_page (max 100).
- Machine auth (Pilot instances): POST /auth/token with grant_type=client_credentials (only refresh_token and client_credentials grants are implemented in token_handlers.go) OR X-API-Key header with qf_ak_-prefixed key (SHA-hash stored, scoped, per-key rate limit, rotation with previous-key grace window). Token claims carry TenantID, Scopes ([]string, all-of enforcement), ClientType (user|service|agent), roles.
- Human auth today: POST /auth/register, /auth/login (Argon2id + HIBP + lockout, TOTP MFA challenge via /auth/mfa/verify), /auth/token (refresh), /auth/revoke, /logout, /logout/all, /sessions, /me, password reset. Access token = qf_at_ + JWT (ES256/EdDSA), refresh = qf_rt_ opaque with signature stored in Redis; JWKS live at /.well-known/jwks.json. NO authorization-code/PKCE flow is live (OIDC service nil).
- Roles are a closed set in internal/domain/role.go: admin, user, service, agent. Casbin model (internal/rbac/model.go) is sub/obj/act with g-role hierarchy, persisted in casbin_policies (has tenant_id column). Scope middleware exists (RequireScopes all-of, RequireRoles, RequireClientType) but is not tenant- or org-parameterized.
- 15 migrations (clients, users, refresh_tokens, email verification, casbin, MFA, oauth_accounts, webhooks, password policy/history, audit_logs, RAR, credential vault, SAML, multi_tenancy). Storage: pgxpool Postgres repos in internal/storage + Redis for refresh tokens/revocation/MFA state.
- cmd/server/main.go nil services (grep 'registered in a subsequent issue'): oidcSvc, brokerTokenSvc, samlSvc, consentSvc, clientApprovalSvc, adminBrokerSvc, adminSAMLSvc, plus AdminServices.Tenants unset and oauth account repo nil — the definitive list of what is scaffolding vs live.
- Wire-up cost to make tenancy live is small: implement TenantResolver over tenant_repository.FindBySlug, add middleware.TenantMiddleware to the public router chain, set AdminServices.Tenants = admin.NewTenantService(...), and set app.current_tenant_id per-connection (or rely on WHERE-clause filtering already present in every repo query).
- Deployment today: docker-compose.production.yml + Caddy on a single host, GH Actions workflow_dispatch deploy over SSH with health-check rollback; staging workflow disabled pending infra. No Kubernetes/AWS artifacts in this repo.

## Asset: studio-sdk
studio-sdk (github.com/qf-studio/studio-sdk, v0.x unstable, Go 1.24, only third-party dep gorilla/websocket) is a set of 10 connectors (asana, azuredevops, discord, github, gitlab, jira, linear, plane, slack, telegram) normalized behind sdk/core. Core contract: Adapter (Name), Pollable (NewPoller(PollerDeps) Poller), WebhookCapable (WebhookSource), Poller (Start(ctx)), ChatCapable (NewChatBridge(ChatDeps) ChatBridge), ChatBridge (Start/Send/Edit/Ack). Normalized types: IssueEvent {Action created|updated, IssueID, SequenceID (provider-prefixed e.g. GL-42/PROJ-42), Title, Body, Labels, Priority (normalized vocab), ProjectID}, IssueResult {Success, Skipped+SkipReason, PRNumber/PRURL/HeadSHA/BranchName, Error}, PRCreatedEvent, MessageEvent/OutboundMessage/Button/MessageRef for chat. PollerDeps is a host-callback seam: ProcessedStore (dedup across restarts), TaskChecker, ExecutionChecker, PreFlightJudger, RateLimitScheduler, IssueMetricsRecorder, Logger — SDK never imports the host. Global registry (Register/Get/All). All 7 tracker connectors support BOTH polling and webhooks (with signature verification: GitHub HMAC, GitLab X-Gitlab-Token, Linear Ed25519, Jira/Asana/Plane HMAC, AzDO basic secret) and all have substantial WRITE surfaces (comments, labels/tags, state transitions; GitHub/GitLab/AzDO also full PR lifecycle incl. merge; issue CREATE exists on GitHub, Linear, Plane; not on Jira/Asana/GitLab/AzDO). Auth is single-credential per connector: PATs (GitHub, GitLab, AzDO), API key (Linear — multi-workspace supported, Plane), email+API token (Jira Cloud/Server), personal access token (Asana). No OAuth-app flows anywhere. There is NO bidirectional sync engine: the SDK is strictly event-in/result-out, one-directional (tracker → IssueEvent → host handler → status writes back). Only fragments point toward sync: Plane AddCommentWithTracking uses external_source/external_id for idempotent comment dedup, and GitHub ProjectBoardSource/ProjectBoardSync reads/writes Projects-V2 status columns — a single-provider kanban precedent. No cross-tracker ID mapping, no conflict handling, no delta/updated-since sync. Pilot consumes the SDK mid-migration (M7): go.mod pins studio-sdk v0.30.0; the SDK GitHub poller is now registered unconditionally (use_sdk_poller flag deprecated GH-4171) and chat bridges (telegram/slack/discord) run via SDK through internal/adapters/sdkshim; but pilot/internal/adapters still contains full duplicated copies of all 7 tracker adapters wired into pilot.go/orchestrator/config, and internal/adapters/github is deliberately retained for autopilot's PR/CI/release surface. ## Asset: infra
aws-infrastructure-pilot is a single-account, single-tenant "agent sandbox" in eu-central-1 (AWS profile quantflow), built with raw CloudFormation YAML (no CDK/Terraform) + one Packer template + three GitHub Actions workflows. It provisions two NIST-separated VPCs with no network path between them: a mgmt VPC (10.10.0.0/16) hosting one t3.small "Infra Admin" GitHub self-hosted runner with AdministratorAccess, and a pilot workload VPC (10.20.0.0/16) hosting one t3.medium "Agent Deployer" runner (scoped IAM) plus an EC2 Auto Scaling Group of Pilot agent instances (default t3.xlarge, 120GB gp3, KMS-encrypted, deployed with min 0 / max 10) with an AWS Warm Pool of 2 stopped instances (resume ~10-20s vs ~90s cold; ReuseOnScaleIn). Agents boot from a Packer-built "Golden AMI" (Amazon Linux 2023 with Node 22, Claude Code CLI, Python3, uv, Docker, AWS CLI, git identity pilot@quantflow.studio, plus a portable /opt/pilot-tools bundle for docker-cp into bench containers). Execution model: a CI job calls `autoscaling set-desired-capacity 1`, ASG resumes a warm instance in a private subnet, the Pilot task is delivered via SSM RunCommand, the agent reads ANTHROPIC_API_KEY/GITHUB_TOKEN from SSM Parameter Store, clones the repo, runs Claude Code, opens a PR, writes artifacts/logs to the pilot-s3-agent-data bucket (patterns/ artifacts-30d/ logs-90d/ moulage/), then capacity returns to 0. There is zero inbound traffic anywhere (no ALB/NLB, no public services): outbound-only via NAT GW to api.anthropic.com/github.com/pypi, and VPC interface/gateway endpoints for S3, ECR, SSM/SSM-Messages/EC2-Messages, CloudWatch Logs, KMS, Secrets Manager. Supporting resources: two KMS keys (alias/mgmt, alias/pilot), an ECR repo pilot-agent (immutable tags, scan-on-push — but the agent actually runs from the AMI, not containers), VPC flow logs, subnet NACLs, IMDSv2 required. Deployment automation is thin: validate.yml (cfn validate on push), build-ami.yml (manual dispatch → Packer build → writes AMI id to SSM /pilot/GOLDEN_AMI_ID), deploy-pilot.yml (manual dispatch, type "deploy" to confirm, sequential `aws cloudformation deploy` of 11 stacks on the self-hosted admin runner). Mgmt plane is deployed by hand via scripts/mgmt-deploy.sh. This is a solid security-conscious single-operator sandbox, not a fleet: no per-tenant anything, no orchestrator/control plane, no load balancer, no database, no monitoring dashboards, and secrets (ANTHROPIC_API_KEY, /pilot/GITHUB_PAT, GITHUB_TOKEN) are stored as plain SSM String type, not SecureString.
**Reusable:** 
- Golden AMI Packer template (/tmp/aws-infrastructure-pilot/packer/pilot-agent.pkr.hcl): AL2023 + Node 22 + Claude Code + Python/uv + Docker + SSM agent with per-boot restart hook, SHA256-pinned tool bundle — directly reusable as the SaaS worker image; parameterized claude_code_version.
- Warm Pool ASG pattern (stacks/workload/compute.yml): scale-to-zero ASG (min 0/max 10) + AWS::AutoScaling::WarmPool (PoolState Stopped, ReuseOnScaleIn) giving ~10-20s task start — the core cost/latency trick for on-demand per-task Pilot workers.

**Gaps:**

**Key facts:**

## Asset: model-backends
Pilot's model engine has two layers: a Backend interface and a ModelRouter. Backend (internal/executor/backend.go) defines Name/Execute(ExecuteOptions)/IsAvailable; five implementations exist: claude-code (CLI subprocess, default), opencode (HTTP server at 127.0.0.1:4096), qwen-code (CLI), anthropic-api (direct Messages API agent loop with own tool dispatch, thinking budgets, 60-turn cap), and openai-api (direct /v1/chat/completions agent loop supporting OpenAI/OpenRouter/Groq/Together/vLLM/Ollama). Backend type is per-instance: chosen once from BackendConfig.Type in NewBackend (backend_factory.go), one Runner = one backend; there is no per-task backend switching. Model IS per-task: ModelRouter (model_routing.go) maps heuristic complexity (complexity.go: trivial/simple/medium/complex/epic via regex/keyword/word-count heuristics, optionally floored upward by a Haiku LLM effort classifier) to model names via ModelRoutingConfig (enabled by default: trivial→claude-haiku, simple/medium/complex→claude-sonnet-4-6; Opus reserved for epic planning via PlanningConfig, default claude-opus-4-7). Same complexity also drives per-tier timeouts (5m–60m) and optional effort routing (low/medium/high/max). An outcome tracker (memory/model_tracker.go, GH-1991) escalates the model when per-taskType failure rate exceeds a threshold. Key handling: for claude-code backend, execution bills to the operator's own Claude Code auth (OAuth/~/.claude/settings.json/ANTHROPIC_API_KEY) unless BackendConfig.APIBaseURL/APIAuthToken are set, in which case Pilot injects ANTHROPIC_BASE_URL/AUTH_TOKEN/MODEL into the subprocess (GH-2371, enables Z.AI/OpenRouter-via-Anthropic-shim). Direct-API backends resolve keys from config or env (ANTHROPIC_API_KEY, OPENAI_API_KEY, PILOT_ENGINE_API_KEY, CLAUDE_CODE_OAUTH_TOKEN). Cost tracking exists and is wired: BackendResult carries input/output/cache tokens; runner computes EstimatedCostUSD (estimateCostWithCache + hardcoded pricing table in memory/metrics.go) per execution into the SQLite executions table; dispatcher.go:1132 emits per-execution usage_events rows (task/token/compute) via memory/metering.go — which already contains SaaS-shaped billing scaffolding (UserID/ProjectID fields, $1/task flat fee, token pricing with 20% margin) though UserID is empty single-tenant today.

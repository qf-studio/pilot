# Learning: Pilot implements the Acceptance list and trusts every claim in the issue body: put each required change under Acceptance, and never assert an unverified fact in an issue

## Summary
Two consecutive pilot-console PRs (PR#332 for #331, PR#334 for #333, 2026-09-28) shipped the new-workflow half of the issue and left the second named file untouched. Cause on our side: in #333 the deploy-workflow fix lived under its own H2 ('Required change in the deploy workflow'), not in '## Acceptance', so the executor's acceptance list never contained it; and #333's Change section stated 'per PR#332 that path omits TenantFactory', which was false, and PR#334 copied the claim into its body and its code comment. The evidence gate verifies command-shaped items only; prose criteria and named-but-untouched files are invisible to it (gate improvement filed on pilot).

## Context
Found in the post-merge review of PR#332 and the pre-merge review of PR#334 (already auto-merged on green before the review landed). Consequence: main carried a Release step that dispatches the deploy without tenant_factory while the deploy still defaults TenantFactory=false, so the next automatic deploy would have switched tenant provisioning off; Auto Release was disabled by hand until the revision (#336) lands.

## Recommended Approach
Authoring rule: (1) every required file change is a bullet under '## Acceptance' with its file path and the observable it produces; (2) verify any claim about existing code before writing it into an issue (read the file on main, cite line numbers), or phrase it as 'confirm whether'; (3) after a REQUEST-CHANGES verdict, check the PR state before assuming it can be held: autopilot merges on green within minutes, so review pre-merge PRs first and use a revision issue rather than expecting a draft flip to work; (4) when a merged PR leaves a live hazard, disable the triggering workflow first, then file the revision.

## Update 2026-09-29 — the evidence gate recognises exactly three phrasings

- pilot#5477 ended its Acceptance with "Evidence in the PR body: one `go test -run` output line per new test". PR#5478 merged without those lines and the gate was silent. Verified in `internal/executor/acceptance_evidence.go`: `pasteOutputPatternRe` matches only "pasted into the pr body", "paste the output", "terminal output"; anything else classifies as `other`, which is never rendered under "## Evidence" or "## Not verified". Widening filed as pilot#5479.
- Authoring rule until #5479 is on the box: write every evidence item as **"Paste the output of `<full command>` into the PR body"**, where the command starts with an allowlisted binary (`go`, `make`, `npm`, `npx`, `bun`, `pnpm`, `yarn`, `pytest`, `cargo`) and is complete (package path, `-run` pattern). A fragment like `go test -run` parses to zero commands and is reported "no commands parsed", never run. Mutation items keep the "<change> -> TestX fails" shape.

## Update 2026-09-29 (evening) — root cause: the heading, not the phrasing

- The noon rule above was incomplete. Three PRs authored with the gate's exact phrasing (PR#5480, PR#5482, console PR#348) still got no "## Evidence" section. Verified on `origin/main`: `ExtractAcceptanceCriteria` (`internal/adapters/github/converter.go`) only recognises "## Acceptance Criteria", "### Acceptance Criteria" and "### Criteria". Our house heading "## Acceptance" yields an empty `Task.AcceptanceCriteria`, so the paste/mutation gate returns before parsing anything. The diff-coverage half reads the body with its own heading list, which is why only "Not verified: <file> named in the issue but not modified" ever appeared.
- Fix filed as a pilot issue (adapters extractor accepts "## Acceptance"). **Until it is on the box, title the section `## Acceptance Criteria`.** Second lesson from the same PRs: the diff-coverage check flags every path named under Change/Acceptance that the PR leaves untouched, including paths you named to say "do not touch". Name a file in an issue only if the PR must modify it.

## Update 2026-09-29 (late) — the heading was necessary, not sufficient: the dispatcher drops the criteria

- With "## Acceptance Criteria" headings (PR#5488, PR#5489) the v2.276.7 extractor yields the items and the runner-built PR body is intact, yet no Evidence section appears. Cause: `ProjectWorker.processQueue` rebuilds every task via `buildTaskFromExecution` from the `executions` row, which has no acceptance-criteria column; `Task.AcceptanceCriteria` is therefore always empty at the runner. **The paste/mutation gate has never run in production for any task**, and GH-920's criteria-in-prompt never fired either. Filed as https://github.com/qf-studio/pilot/issues/5491 (leaf package for the extractor + derive in `buildTaskFromExecution`).
- Reviewer rule until it ships: treat every "## Evidence" expectation as unmet by default and run the paste commands and mutation pins yourself (as done for all six PRs today).

# Learning: GitHub write calls can fail three times in a row with "Something went wrong" / an empty body while reads work and status is green — re-check for the created object before every retry

## Summary
2026-11-05 16:09Z: `gh issue create` returned the GraphQL "Something went wrong while executing your query" twice and `gh api POST /issues` returned "unexpected end of JSON input" once; rate limits were fine (core 3819, graphql 4792), githubstatus said operational, reads worked. The fourth call (REST POST with `--include`) returned 201 and created #6106. None of the failed calls created an issue, but that was only known because a title search ran between attempts.

## Context
Filing the studio-sdk v0.38.6 pin-bump issue after the TASK-620 enforce flip. Same class as the 11-04 "GitHub 500 burst" that failed an autopilot merge (TASK-635 H1).

## Details
- A failed write is not proof that nothing was written: GitHub can create the object and fail the response.
- `gh issue create` uses GraphQL for label resolution; the REST endpoint is an independent path.
- The daemon already treats API outages as hold + backoff + redrive (TASK-635); operators retrying by hand have no such guard and can file duplicates, which Pilot then executes twice.

## Recommended Approach
Between retries, search for the object (`gh issue list --search "<title fragment> in:title"` or `gh api .../issues?state=open&labels=pilot` filtered by title). Prefer the REST POST (`gh api repos/O/R/issues -f title= -F body=@file -f "labels[]=…"`) when GraphQL errors; use `--include` so a 201 with a malformed body still shows the Location header. After success, scan the neighbouring issue numbers for a duplicate.

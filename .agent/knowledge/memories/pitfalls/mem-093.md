# Pitfall: on_merge auto-release wedges in `releasing` — external-merge drain removes the PR before `handleReleasing` cuts the tag

## Summary
Every `require_ci: true` `on_merge` release silently wedged: PRs reached `StageReleasing` but no tag was ever cut, so the fix-of-the-day sat merged-but-unreleased and someone hand-cut a tag (v2.236.0/.1/.2/.3 all manual). Root cause: `checkExternalMergeOrClose` (`internal/autopilot/controller.go:4306`) runs first every poll tick and had guards for `ScopeKey` and `StagePostMergeCI` but **no `StageReleasing` guard** — for a merged non-scope PR at `StageReleasing` the release-trigger block is skipped (L4363 `Stage != StageReleasing` is false) and execution falls through to `removePR` (L4401) + `return true`, so `ProcessPR → handleReleasing` never runs. `ScanRecentlyMergedPRs` then re-adopts the untagged merged PR at `post_merge_ci`, looping until it ages out of the 30m window.

## Context
Declared an incident 2026-07-09 after #4120/#4122 merged with green CI but the release stayed at v2.236.1. Diagnosed via release-stage lifecycle map (subagent) + live daemon logs. Regression introduced by **GH-3994**, which added the sibling `StagePostMergeCI` guard for the same re-entrancy reason but omitted `StageReleasing`.

## Details
Only `require_ci: true` (the default, and pilot's config) is affected: that path sets `StagePostMergeCI` on tick N and transitions to `StageReleasing` on a **later** tick, so the *next* tick's `checkExternalMergeOrClose` drains it before `handleReleasing` fires. The skip-CI path sets `StageReleasing` and runs `handleReleasing` in the **same** tick, so it never wedges — which masked the bug. The prior marker's "daemon restart interrupts the release" theory was **refuted**: the daemon was alive ~170 poll ticks with #4120 (15:45→17:11) and #4122 (16:49→…) both stuck. Bootstrap trap: the fix (#4125) could not release itself — the running daemon still carried the wedge and drained #4125's own release, so a manual v2.236.3 tag was required; the fleet self-heals only once every daemon runs the guarded build.

## Recommended Approach
(1) When adding a stage to a polled state machine, audit every "pre-empt / drain" function that runs before the per-stage handler and add the matching guard (mirror the `StagePostMergeCI` pattern). (2) Test the drain path, not just the handler — existing tests called `handleReleasing` directly and never exercised `checkExternalMergeOrClose` on a `StageReleasing` PR, which is why it shipped. (3) `on_merge` releases: verify the **next organic merge self-cuts a tag** before declaring a release-controller fix done. (4) A merged-but-unreleased PR + `latest release` behind main HEAD = the tell; out-of-band tags are safe (releaser reads the baseline live from git tags) and both ship the code and drain the stuck `releasing` state.

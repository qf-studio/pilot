# Pitfall: Retry contexts rooted in context.Background() drop per-execution context values (billing credential lost on smart retry and gate-feedback retry)

## Summary
Retry contexts rooted in context.Background() drop per-execution context values: the smart retry (runner.go ~5470) and the quality-gate feedback retry (~6449) lost the billing credential set by WithBillingCredential, so in api_key mode a retry silently billed the subscription. Derive retry ctx with context.WithoutCancel(taskCtx) (idiom at runner.go 374/3299/3336). Also: a billing-key outage row finished as 'failed' feeds repick backoff and the identical-failure streak; use the infra class, not a new status (TASK-633 F1).

## Context
Found 2026-11-03 by navigator-research while verifying the nine post-merge review notes on PR#6017 (GH-6016, billing mode) on main f72c25810. The reviewer did not list it; tracing "what spawns after Zero()" surfaced it. Fix dispatched as TASK-633 leg F1 (pilot#6021).

## Details
Any value attached to the task ctx (billing credential, and anything else WithValue carries) is gone on a retry ctx built from context.Background(). The two sites: the smart retry around runner.go:5470 (backendExecute at :5475) and the quality-gate feedback retry around runner.go:6449-6450. modelSubprocessEnvFor then strips the inherited ANTHROPIC_API_KEY, the CLI falls back to the login file, and the run bills the subscription with no error. After Zero() the credential's Env() returns nil, the same as subscription mode, so a stale ctx fails open, not closed.

The outage-row half: failBillingKeyUnavailable (billing_admission.go:102/110) takes a real claim and finishes the row 'failed'; nextRetryGeneration treats that as not done and grows consecutiveDrops plus backoff; two identical error texts trip consecutiveIdenticalFailureThreshold and park the task. ExecStatusSkipped takes the same path. ExecStatusInfra reuses the GH-5211 carve-out (own counter, cap 8, no streak check) without a new terminal status.

## Recommended Approach
Build every retry or follow-up ctx inside an execution with context.WithoutCancel(taskCtx) plus the timeout, never from context.Background(). When a pre-run failure must not count as a task failure, finish the row with the infra class instead of inventing a status (terminal-status-without-rearm-probe pitfall).

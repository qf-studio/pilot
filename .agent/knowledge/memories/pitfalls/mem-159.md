# Pitfall: Scope-release train dies terminally on transient red main (+ RCA lesson: pull ground truth before filing the fix)

## Summary
Pilot's daily self-release (train cron `0 16 * * *` Europe/Berlin = 14:00Z) silently died 07-14 and 07-15. Real mechanism (4-investigator RCA, 92% confidence): the release carrier gates on post-merge CI of main HEAD; any red — 07-14: canary misattribution (since fixed by #4319–#4325); 07-15: a genuine `internal/briefs` `sql: database is closed` flake — burns all 5 `maxScopeReleaseAttempts` within minutes because retries are per-tick against the same SHA. The train then goes terminal `failed`, a state **nothing ever re-drives** (`startPendingScopeReleases` claims only pending/releasing). Main going green later changes nothing; scope only rolls into tomorrow's train.

## Context
2026-07-15: founder reported 'release not out at 16:43' (recurring). Release cadence established from `gh release list` (dailies ~14:04Z, v2.237–239, then nothing). v2.239.0 AND v2.240.0 were both manual tags, not daemon releases — the train had been failing since 07-13. Decisive evidence: `autopilot_scope_release` rows (train:07-13 failed/attempts=19, 07-14 failed/11, 07-15 failed/6 terminal at 14:07:04Z), daemon.log `enqueued scope release` lines at 14:00Z (scheduler innocent), and check-run pulls on `02896358` (canary correctly EXCLUDED; repo's own `test` check red since 00:20Z).

## Details
**RCA discipline lesson (as important as the bug):** my fast inline diagnosis blamed a `CheckCI` vs `GetFailedChecks` exclusion split-brain and I filed pilot#4331 on it. The evidence-based workflow REFUTED that for the day in question — the exclusion works (`ci_monitor.go:355-371`); the gate failed on a real flake, and the unrecoverable-terminal-train design gap is the true defect. The issue had to be rewritten before Pilot executed a wrong fix. **Rule: for daemon-behavior RCAs, do not file the fix from code-reading alone — first pull ground truth: `~/.pilot/data/pilot.db` (`autopilot_scope_release`, `autopilot_pr_state`), `~/.pilot/logs/daemon.log`, and the actual check-runs on the SHA.**

Latent defects found alongside (all specced in pilot#4331): `MarkScopeReleasePending` (state_store.go:1104) has no state guard and is called before the cap check → restart-rehydrated zombie carriers bounce dead trains failed→pending→failed; `MarkScopeReleaseDone` (state_store.go:1089) unconditionally overwrites `tag` → restart replay blanks done rows. Config trap: `ci_checks.required: []` silently disables the legacy `required_checks` allowlist (`ci_monitor.go:50-61`) — pilot#4333.

## Recommended Approach
For any 'X did not fire' autopilot complaint: (1) establish historical cadence from `gh release list`; (2) check `autopilot_scope_release` state/attempts for the day's train BEFORE reading code — terminal `failed` + green main = this pitfall; (3) only then read code. Manual unblock: `git tag vX.Y.Z origin/main && git push origin vX.Y.Z` — goreleaser publishes everything; **NEVER `gh release create` manually** (races goreleaser, 422 asset-exists — Makefile:176). CLI alternative: `pilot release --dry-run` then `pilot release`. Stuck-train re-drive (only when main is green and scope isn't already covered by a manual tag): flip the sqlite row to `pending`, attempts=0; the sweep claims it in ~30s. Fixes: pilot#4331 (recovery+guards), #4332 (deflake trigger), #4333 (config precedence).

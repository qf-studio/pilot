# Pitfall: The autopilot CI-log trimmer can quote a fixture FAIL line from a test's own log output as the failing test — the fix issue then names a test that does not exist

## Summary
Autopilot fix issue #6098 (post-merge CI on main e9f892a90, 2026-11-05) quoted `--- FAIL: TestX` as the test failure. That string is a fixture inside a dispatcher test's WARN log message (a fake quality-gate output), not a Go test result; the real failure was `--- FAIL: TestListRecordingsWithFilters` (recorder_test.go:525, a 10 ms wall-clock Since window). The trimmer (TASK-634 C1 keeps "failure lines") matched the first `--- FAIL:` substring in the job log, which sat inside a log line. Pre-flight declined the issue as reject_vague, so no harm, but the operator had to read the raw run to learn the real test.

## Context
Founder asked "what is 6098 and why was it declined"; traced from the issue body, the pre-flight comment and `gh run view <id> --log-failed`.

## Details
- Go test output has `--- FAIL: Name (0.06s)` at column 0 (or indented for subtests); a fixture string lives inside a `msg="..."` log line with a timestamp prefix.
- The same run also failed the ShellCheck action on a binary download (`tar: This does not look like a tar archive`) — GitHub infra, no code change possible.
- Two flakes on a scripts-only PR produced a fix issue with two wrong leads.

## Recommended Approach
When reading an autopilot-fix issue, trust only `--- FAIL:` lines that start a log line (after the runner timestamp), never one embedded in `msg=`. For the trimmer: anchor the failure regex at line start after the timestamp (`^\S+ (--- FAIL|FAIL\s|panic:)`), and when every failure is an action download / infra error, say so in the issue instead of pasting the log. Test-flake fixes replace wall-clock windows with a captured cutoff (pilot#6101).

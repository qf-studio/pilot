# Pitfall: handlePostMergeCI pinned the main head, not the PR's merge commit: two merges 23 s apart filed two fix issues for one docs-sync run

## Summary
Autopilot filed #6107 (PR#6104) and #6108 (PR#6105) for the same red run 42062140402 (GitHub 'remote: fatal error in commit_refs' on the docs-sync push). handlePostMergeCI filled an empty PostMergeSHA from getMainBranchSHA, so a PR whose first post-merge tick ran after a later merge watched that later merge's CI. Pilot shipped the same workflow retry twice (PR#6114 merged, PR#6115 duplicate). Fixed by #6125 → PR#6132: PostMergeSHA comes from the PR's MergeCommitSHA, a code-class red gets one re-run before a fix issue, fix issues dedup by the workflow-run permalink; #6137 → PR#6140 restarts the CI timer after a re-run.

## Context
TASK-508 follow-up, 2026-11-05 16:12Z merges; found while reviewing the first enforce-mode day.

## Details
The scan-recovery and external-merge paths already set PostMergeSHA from pr.MergeCommitSHA; handleMerged did not, and the first tick fell back to the branch head. findExistingFixIssue matched by exact title, and the title carries the PR number, so two PRs never collided. The infra classifier is an LLM rubric; the commit_refs rejection was classed as code.

## Recommended Approach
When two post-merge fix issues quote the same actions/runs id, close the second as a duplicate and check which merge commit the run belongs to. On daemons before v2.314.0, expect this on any two merges inside one poll interval.

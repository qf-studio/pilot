---
name: Phantom binary version (git-describe from a since-deleted tag) silently blocks `pilot upgrade`
description: "make build derives VERSION from `git describe --tags`. A binary built while a tag existed embeds that version even after the tag is deleted. `pilot upgrade check` compares the embedded version against the latest GitHub release; if phantom >= latest, update_available=false and the daemon is pinned to that build forever — it can never self-upgrade, so merged fixes never reach it. Hit 2026-06-09: the daemon's `Pilot 2.178.0` (built while the spurious v2.178.0 tag existed, then deleted) wouldn't upgrade to the real Latest v2.177.0, stranding the ancestor-dedup fix on main."
type: pitfall
---
A deleted/reverted release can leave a **phantom-version binary** that silently refuses every future upgrade. The daemon reports a version *higher* than any real release, so `pilot upgrade` decides it is "already newest" and never pulls the build that contains your fix.

**Why:** `Makefile` sets `VERSION?=$(shell git describe --tags --always --dirty)` and bakes it in via `-ldflags "-X main.version=$(VERSION)"`. A binary built **while a tag existed** embeds that tag's version permanently — deleting the tag afterward does nothing to the installed binary. `pilot upgrade check` (`cmd/pilot/upgrade.go` → `upgrade.CheckVersion`) compares the embedded `version` against the latest GitHub release and sets `update_available` only when latest **>** current. If the phantom version is `>=` the real latest, the check returns `"✅ You're running the latest version!"` and `--force` (which only skips the running-task wait, not the version gate) does not help. The daemon is pinned.

**Why (the 2026-06-09 incident):** the spurious-release pitfall [[bug_manual_merge_spurious_release]] produced a `v2.178.0` tag that was then deleted (real Latest reverted to `v2.177.0`). But the daemon binary had already been built (10:03Z) from `git describe` **while `v2.178.0` existed**, so `~/.local/bin/pilot version` reported `Pilot 2.178.0`. The ancestor-dedup fix merged to `main` (#3506) at 13:55Z, but `pilot upgrade check --json` returned `{"current":"2.178.0","latest":"v2.177.0","update_available":false}` — `2.178.0 >= 2.177.0` → no-op. The fix was on `main` but could not reach the running daemon through the supported path.

**How to apply:**
- After deleting/reverting a release, check whether a binary was **already built and installed** from it: `~/.local/bin/pilot version` may report a phantom version higher than the real Latest.
- To redeploy past a phantom version **N**, cut **N+1** — do **not** reuse N. A real release equal to the phantom version still no-ops the upgrader (`latest == current`, not `>`). 2026-06-09 fix: cut `v2.179.0` (skipping the cursed 2.178.0); `2.178.0 < 2.179.0` → `update_available:true` → daemon upgraded + restarted on the fix.
- **Do not** "fix" it by a plain `make build` from `main`: `git describe` then yields `v2.177.0-N-g<sha>`, a semver **pre-release** of 2.177.0 that sorts *below* the released `v2.177.0` → the upgrader would then offer to "upgrade" to the fix-less released `v2.177.0` = regression trap. Skip past the phantom number with a real tag instead.
- Verify the deadlock is cleared with `pilot upgrade check --json` (expect `update_available:true`), then `pilot upgrade --yes`, then confirm `pilot version` + `ps -o lstart` start-time > binary mtime (see [[learn_restart_vs_rebuild_stale_binary]]).

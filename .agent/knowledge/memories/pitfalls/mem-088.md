# Pitfall: Dashboard/ledger stage strip can mark SHIPPED work as failed (✗ pr_created) — verify execution_events + GitHub before trusting it

## Summary
The QUEUE stage strip (internal/dashboard/stage_strip.go buildStageStrip) renders the LAST rung-bearing event before a terminal failure, not the max rung reached. When a duplicate/late finalization step fails AFTER the real PR merged+released, the strip shows e.g. 4/7 ✗ pr_created for work that factually reached 7/7 released. Seen on GH-4006 (PR #4012 merged+v2.231.1, then executor opened ghost duplicate #4014 which conflict-failed) and GH-3992 (stale pilot-retry label re-dispatched a shipped task; orphan-row delete raced the poller waiter into a false task_failed alert).

## Context
2026-07-07 marker burn-down: user saw '4/7 ✗ pr_created GH-4006' on the dashboard; subagent forensics proved the issue shipped. Root causes filed as #4020 (executor duplicate-PR finalization + strip max-rung fix) and #4021 (auto-retry bypasses completed-execution guard + waiter sql-no-rows race).

## Recommended Approach
Before treating a ledger ✗ as a failure: (1) check GitHub truth — gh issue view N (state/labels) and gh pr list --head pilot/GH-N --state all; (2) check execution_events in ~/.pilot/data/pilot.db for merged/released rungs EARLIER than the failed one; (3) false task_failed alerts after 'Deleting orphan running row (task already completed)' mean the task shipped. Fixes tracked in #4020/#4021.

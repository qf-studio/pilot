# Pitfall: vi.spyOn on an already-spied method layers spies; mockRestore unwinds one layer, and the leftover spy pollutes the next test

## Summary
In ChatView.spec.ts the beforeEach spies mockAdapter.listCredentials; a helper (seedKeyHealth) called vi.spyOn on the same method again inside a test. afterEach mockRestore removed only the outer layer, so the next test's mockRestore() landed on a stale spy that resolved the seeded list instead of the real mock — GH-387 'real adapter' test failed only when run after the new GH-389 test (passed alone). Fix: re-mock the existing spy with vi.mocked(fn).mockResolvedValue(...) instead of a second spyOn; bisect by running the pair with -t.

## Context
TASK-640 K5, pilot-console-ui PR#391 CI red, bisected locally 2026-11-06 (variants: unmount / no-preload did not help; re-mocking the existing spy did, 27/27)

## Recommended Approach
One vi.spyOn per method per file (in beforeEach); every test re-mocks via vi.mocked(...). A spec helper that 'seeds' a mock must not call vi.spyOn. When a test fails only in sequence, run the pair with vitest -t to confirm pollution before touching the code under test.

# Pitfall: Production UI build ships the mock adapter — a whole e2e 'pass' can be in-browser fixtures

## Summary
console.pilotcloud.dev served the MOCK adapter build for two days: adapter.ts defaults to mock unless VITE_API_MODE=http, and the deploy workflow only set VITE_API_BASE. Register/login/Docs/Connections/Provision all 'succeeded' against fixtures; the 09-22 first-login milestone and the 09-23 first-tenant provision were false successes.

## Context
2026-09-24. Founder reported 'instance is active' after Provision; screenshot showed inst_1 · us-east-1 · Pilot 1.4.2 · events 100d ago = mockAdapter.ts fixture. AWS side: no tenant EC2, zero RunInstances from the reconciler in CloudTrail, reconciler alive with the factory on and nothing logged. Live bundle had 0 occurrences of /api/v1/ and contained the mock dataset.

## Details
Vite statically replaces import.meta.env.VITE_API_MODE; with it unset the condition is false and the HTTP adapter is tree-shaken out, so the deployed bundle physically cannot call the API. The UI looked fully functional, the edge served it, and the API behind it was healthy (GET /api/v1/me = 401 JSON) — nothing on the infra side could reveal it. Tells: wrong region string, ancient relative timestamps, a version that never shipped, a fixture id like inst_1, and zero network requests to /api/v1/ during login.

## Recommended Approach
1) Every production UI build must pin the adapter mode explicitly (VITE_API_MODE=http) in the deploy workflow. 2) Guard the bundle: fail the build unless /api/v1/ is present and fixture markers (inst_1, us-east-1) are absent. 3) Never accept a browser milestone without one wire proof: a network-tab request to the API or a server-side log line for that action. 4) When an operator reports success but the backend shows no side effect, suspect the client before the backend. Fix: pilot-console-ui#170.

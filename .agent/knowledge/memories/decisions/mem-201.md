# Decision: aws-infrastructure-pilot is Nelya's repo: we file asks, we never push commits or PRs there

## Summary
Founder rule 2026-09-28: the infrastructure repo (qf-studio/aws-infrastructure-pilot, the pilot-fleet/pilot/quantflow/pointer/mgmt CloudFormation families) is owned and operated by Nelya. Our side never opens PRs, merges, reverts, or pushes to it, and never dispatches Pilot against it. Every template change is an ASK: a GitHub issue on that repo or a Slack message in #infrastructure written as purpose -> what exists -> what to build -> how we verify. Nelya edits the template and deploys.

## Context
2026-09-28 review of the repo history: between 08-03 and 09-28 we merged 11 PRs there ourselves (AMI bake #3/#5/#6/#7/#11/#13, console-api sync-worker flags #15, DesiredCount #17 + revert #20, WAF scope-down #19). Two of them were wrong for her estate on the day they landed: #17 was superseded by her console-api/console-workers split within hours, and #19's scope-down (whole Linux rule set off the docs route) was replaced by her narrower fix (only LFI_QUERYSTRING relaxed, only for a docs-file request with no '..' after decode) the same morning. Both cost her a corrective commit on main. The founder asked what we pushed there and said: we should not do this, Nelya works on it.

## Details
Why the rule holds: (1) she owns the deployment, so a merge on our side is not a change, it is a queued surprise for her next run; (2) her templates carry cross-stack imports, parameter contracts and placement rules (AZ spread, boundaries, KMS conditions) we do not model, and our two 09-25/09-28 PRs both broke that contract; (3) the audit trail for the account is hers. What stays ours: the console/UI/pilot repos and their GitHub Actions workflows (deploy-quantflow-aws.yml, Deploy console UI), including new deploy jobs that consume her templates from the S3 template base, with parameter overrides matched to her Parameters block (console-workers: ImageTag, JobId, AlertsTopicArn only). Filing issues on aws-infrastructure-pilot remains fine as the ask channel. Do not label them pilot, do not keep the repo in the box's project list with auto-dispatch; drop the aws-infrastructure-pilot project from box config rather than adding ci_checks.required for it.

## Recommended Approach
Before touching any stacks/**/*.yml: stop. Write the ask (purpose, what exists today with ARNs/param names, what to build, how both sides verify) as an issue on aws-infrastructure-pilot or in the #infrastructure thread, tag Nelya, and continue on our repos. If a template gap blocks a run, the blocked run waits; do not hand-merge to unblock. If a Pilot issue was already filed there with the pilot label, remove the label and comment that it is an ask.

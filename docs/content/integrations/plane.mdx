# Plane Integration

Pilot integrates with [Plane](https://plane.so) to receive work items and automatically implement them. It supports both Plane Cloud and self-hosted instances, with polling and webhook modes for issue detection.

Polling is the main path. The poller picks up each work item with the Pilot label, moves it through the Plane states, sets the status labels and writes the result as a comment. The webhook path only queues the work item for execution; see [Webhook Mode](#webhook-mode).

## Before You Start

- **The Pilot label** in each Plane project: a label with the name of `pilot_label` (default `pilot`). The poller does not start without it.
- **The status labels** (optional): `pilot-in-progress`, `pilot-done` and `pilot-failed`. When a label is missing, Pilot skips that step.
- **An API key** for the workspace.
- **The workspace slug**.
- **The project IDs** (UUIDs) of the projects to watch.

## Setup

### 1. Create a Plane API Key

1. Go to your Plane workspace → **Settings** → **API Tokens**
2. Click **Create token**
3. Copy the API key

### 2. Find Your Project UUID

Your project UUID is visible in the Plane URL when viewing a project:
```
https://app.plane.so/{workspace}/projects/{project-uuid}/issues
```

### 3. Set Up Webhooks (Optional)

For real-time issue detection:

1. Go to **Workspace Settings** → **Webhooks**
2. Click **Create webhook**
3. Set the URL to `https://your-pilot.example.com/webhooks/plane`
4. Select events: **Issues**
5. Copy the signing secret

<Callout type="warning">
Always set a `webhook_secret` in production. When empty, signature verification is disabled (development mode only).
</Callout>

### 4. Configure Pilot

```yaml
# ~/.pilot/config.yaml
adapters:
  plane:
    enabled: true
    base_url: "https://api.plane.so"   # Or self-hosted URL e.g. "https://plane.mycompany.com"
    api_key: "${PLANE_API_KEY}"
    webhook_secret: "${PLANE_WEBHOOK_SECRET}"
    workspace_slug: "my-team"          # Your Plane workspace slug
    project_ids:                       # Projects to poll for pilot-labeled issues
      - "project-uuid-1"
    pilot_label: "pilot"               # Issues with this label are picked up
    polling:
      enabled: true
      interval: 30s
```

## Configuration Reference

| Field | Type | Default | Description |
|-------|------|---------|-------------|
| `enabled` | bool | `false` | Enable the Plane adapter |
| `base_url` | string | `https://api.plane.so` | Plane API URL (cloud or self-hosted) |
| `api_key` | string | required | Plane API key from workspace settings |
| `webhook_secret` | string | — | HMAC-SHA256 secret for webhook verification |
| `workspace_slug` | string | required | Your Plane workspace slug |
| `project_ids` | []string | required | Project UUIDs to monitor |
| `pilot_label` | string | `"pilot"` | Label name that triggers Pilot (case-insensitive) |
| `polling.enabled` | bool | `false` | Enable polling for new issues |
| `polling.interval` | duration | `30s` | Poll interval |

## Polling Mode

When polling is enabled, Pilot periodically queries Plane for issues matching:

- **Project**: belongs to one of the configured `project_ids`
- **Label**: has the `pilot_label` (default: `pilot`)

Issues are processed oldest-first by creation date. Parallel execution is supported with configurable concurrency.

### Label Lookup at Start

On start, the poller reads the labels of the configured projects and looks up the Pilot label and the status labels by name (case-insensitive). If no configured project has a label with the name of `pilot_label`, the poller does not start: the log says `pilot label "pilot" not found in any configured project`, and Pilot retries the start with a backoff.

The poller takes the labels from the first configured project that has the Pilot label, and uses those label IDs for every project. Plane labels belong to one project, so with several projects, check in the logs that work items of each project are picked up.

### Priority

Plane sends the priority as text: `none`, `urgent`, `high`, `medium` or `low`. In this release no path maps the text priority to the task priority: the poll path cannot decode it (see the warning below), and the webhook path does not read the priority.

<Callout type="warning">
In this release the poll path still decodes the priority only as a number. With a Plane server that sends the priority as text, the list of work items of a project fails to decode: Pilot logs `Failed to fetch work items` at each poll and picks up no work item of that project. This applies to each Pilot release that pins `github.com/qf-studio/studio-sdk` v0.38.7 (see `go.mod`): that SDK version has no decoder for the text priority. The fix is merged in the SDK but is not in an SDK release yet; the warning stops applying with the first Pilot release that pins an SDK release after v0.38.7.
</Callout>

### Crash-Safe Deduplication

Pilot uses a `ProcessedStore` backed by SQLite to track which issues have been handled. This prevents re-dispatching issues after a restart or hot upgrade — no configuration required.

## Several Plane projects

By default, every work item goes to the default project, whichever Plane project it comes from. To send the work items of each Plane project to its own repository, give the project entry a `plane` block with the UUID of its Plane project:

```yaml
projects:
  - name: web
    path: /srv/repos/web
    plane:
      project_id: "project-uuid-1"
  - name: api
    path: /srv/repos/api
    plane:
      project_id: "project-uuid-2"
```

- For each work item, the poller takes the project entry whose `plane.project_id` is the Plane project of the work item. The branch, the base branch and the pull request follow that project.
- A work item whose Plane project matches no entry goes to the default project. When at least one entry has a `plane` block, the log line for that task is a warning.
- Two entries with the same `plane.project_id`, or a `plane` block with an empty `project_id`, make the config fail to load; the error names the entries.
- Each Plane project still has to be listed in `adapters.plane.project_ids` to be polled.
- Only the polling path routes by Plane project. The webhook path sends every work item to the default project.

## Webhook Mode

For real-time issue detection, configure Plane webhooks to notify Pilot when issues are created or updated.

A work item from a webhook goes to the task queue only. Pilot does not set the status labels, does not change the state and does not write a comment for it, and it does not record the work item as processed. The webhook path does not read the priority.

### Endpoint

```
POST /webhooks/plane
```

### Signature Verification

Plane signs webhook payloads with HMAC-SHA256 and sends the signature in the `X-Plane-Signature` header. Pilot verifies the signature using the configured `webhook_secret`.

<Callout type="info">
If `webhook_secret` is empty, signature verification is skipped. This is intended for development only.
</Callout>

### Supported Events

Pilot reads the `event` and `action` fields of the payload:

| Event | Action | Behavior |
|-------|--------|----------|
| `issue` | `created` | Process if the work item has the Pilot label |
| `issue` | `updated` | Same as `created`: process if the work item has the Pilot label |
| `issue` | Any other (for example `deleted`) | Ignored |
| Any other | — | Ignored |

An `updated` event is not checked for a label change. Every update of a work item that has the Pilot label queues the work item again.

The work item must also belong to one of the `project_ids` (all projects when the list is empty). The event carries label UUIDs; Pilot looks up the UUID of the label with the name of `pilot_label` in the project of the event through the Plane API, and keeps it for 10 minutes. Without an `api_key`, `pilot_label` must be the label UUID itself.

## State Transitions

On the poll path, Pilot updates issue state groups as it works:

| Event | State Group |
|-------|-------------|
| Task dispatched | `started` |
| Execution succeeded | `completed` |
| Execution failed | State unchanged (manual triage) |

### Labels Applied

On the poll path, Pilot applies labels to track issue status:

| Label | When |
|-------|------|
| `pilot-in-progress` | Task dispatched |
| `pilot-done` | Execution succeeded |
| `pilot-failed` | Execution failed |

## Task ID Format

The task ID is built from the sequence number of the work item, the number of the work item in its project; the Plane project identifier is not used. The two paths give different task IDs:
- Poll path: work item `WEB-42` (sequence number 42) → Task ID `PLANE-42`
- Webhook path: work item `WEB-42` (sequence number 42) → Task ID `TASK-PLANE-42`
- Branch name, on both paths: `pilot/PLANE-42`

## Autopilot Integration

PRs created from Plane issues are automatically wired into the autopilot pipeline. CI monitoring, auto-merge, and the feedback loop all work the same as with GitHub and Linear issues — no extra configuration required.

## Running Pilot with Plane

```bash
pilot start --plane --github
```

This starts the Plane adapter alongside the GitHub adapter for PR creation.

## Troubleshooting

### Issues Not Picked Up

1. Verify the project UUID matches exactly (check the URL in Plane)
2. Confirm each project has a label with the name of `pilot_label` (case-insensitive); look for `pilot label ... not found in any configured project` in the logs
3. Check that `polling.enabled` is `true` or webhooks are configured
4. Look for polling activity in Pilot logs

### Webhook Not Triggering

1. Verify the webhook URL is accessible from Plane's servers
2. Check the signing secret matches between Plane and Pilot config
3. Confirm the correct event types are selected in Plane webhook settings
4. Check Pilot logs for signature verification errors

### Self-Hosted Instances

1. Ensure `base_url` includes the protocol (`https://`)
2. Do not include a trailing slash in the URL
3. Verify the API key has workspace-level access
